# Security Policy

Stroq is a security product: its job is to block specific dangerous actions once specific untrusted content has been seen. If you can make a documented protection fail — a command the README says is denied that gets through, or poisoned content a rule should flag that the scanner misses — **that is a vulnerability in this project**, not a feature request, even if the underlying cause looks like "just a regex gap."

## Supported Versions

| Version                                                               | Supported |
| --------------------------------------------------------------------- | --------- |
| The latest release on [npm](https://www.npmjs.com/package/@stroq/cli) | Yes       |
| Anything older                                                        | No        |

Stroq is pre-1.0. Fixes land in the next release rather than being backported, so please reproduce against the latest version before reporting.

## Reporting a Vulnerability

Report privately through GitHub Security Advisories, not a public issue:

**<https://github.com/AGGIB/stroq/security/advisories/new>**

Please include:

- The exact hook event JSON (or the command / content) that should have been blocked, asked, or flagged
- What Stroq actually did — the `stroq log` line, or the raw hook output
- What you expected, and which part of the docs ([docs/GUIDE.md](docs/GUIDE.md), [docs/AGENTS.md](docs/AGENTS.md)), `policies/default.yaml`, or a rule file documents that expectation
- Your Stroq version, Node version, and operating system

### Response Targets

- **Acknowledgement:** within 72 hours of submission.
- **Fix for a confirmed bypass:** within 14 days of confirmation.
- **Coordinated disclosure:** we will agree on a disclosure timeline with you, credit you in the release notes unless you ask to stay anonymous, and ask that details stay private until a fix or documented mitigation has shipped.

## Safe Harbor

Good-faith security research against Stroq — running the CLI against your own fixtures, or crafting inputs to a local instance you control, in order to find bypasses of its documented protections — is welcome and authorized. We will not pursue legal action for research that is conducted in good faith, reported responsibly through the process above, and that avoids privacy violations, data destruction, and disruption to systems or people other than your own test environment.

## Local data retention

**Recorded installation diagnostics** retain finite producer-owned kind/code/scope/agent/client facts in the existing private, unencrypted workspace run history (32 runs / 8 MiB, without automatic expiry). The public projection excludes raw CLI detail, commands, paths and dynamic artifact/server names; human-readable error strings are never parsed into security decisions. Partial or unknown typed metadata is refused rather than treated as legacy success. Existing legacy reports remain readable without migration. A passing legacy installation-wide check may include an absent agent covered by another agent; the UI preserves this distinction. Current-settings navigation binds the current connection and run context but does not establish current health or host enforcement. See [diagnostics](docs/platform/installation-diagnostics.md).

**Platform task permissions** inspects signed Task Lock metadata using only `keys/permit.pub`. Its compact projection excludes raw task IDs, nonces, signatures, commands, prompts, keys and absolute paths; external patterns are withheld. Preview is read-only and transient (eight plans / 8 MiB / two minutes). Explicit revoke creates the native empty `revoked` marker after exact source/root/key/marker/runtime rechecks under the shared harden lock, then verifies store and isolated core gate refusal. Revoke issues no new permit or extension and creates no console report history. Existing task permits and terminal markers remain in the native task store without automatic expiry deletion. Full journal bytes stay in memory and are not copied to scratch. Declared mode, valid signature and revocation are separate from OS enforcement, process liveness and termination. See [task permissions](docs/platform/task-permissions.md).

**One-use task access** has a separate explicit review/signing operation for fresh refusals carrying a parent-signed request bound to the verified permit body, key, operation, complete redacted review and call/session hashes. Preview reads private-key metadata only. Two explicit acknowledgements precede reading the existing key and exclusively publishing one short native extension under pinned parents; no key is created, repaired or sent to the browser. The operator review intentionally includes redacted tool input, working directory and resource context. That text and signed refusal evidence remain in the existing private, unencrypted audit journal, while extensions and consumed markers remain in the native task store without automatic expiry deletion. Redaction covers recognized shapes and known values, not all potentially sensitive text. No separate console approval history is created. Consumed state is not proof of tool execution, and unknown writes require read-only recheck without automatic issue retry. See [one-use access](docs/platform/task-access.md).

The explicit finding-to-permission lookup reselects an exact visible journal record, checks the full bounded chain and raw-line fingerprint, and returns current signed metadata only for the same workspace/task ID without known session or validity-window contradictions. Invalid-ID sentinels and unavailable evidence cannot become a match. This ID association does not verify historical permit attribution, including for records carrying newer signed access evidence; the separate access-request verifier is required for issuance. The source finding carried by navigation is not mutation authority or a resolved-incident receipt. Lookup is read-only, creates no report history and excludes raw task/session IDs and journal contents. Existing revoke consent and exact current-permit checks still apply independently.

**Isolated platform hook checks** retain up to 32 derived attempts per canonical workspace in a private, unencrypted `<STROQ_HOME>/console/hook-checks-<workspace identity>.json` file, without time expiry. They retain captured source/policy/runtime fingerprints, times, fixed probe IDs and decision/audit outcomes, not raw commands, policy text, subprocess output, credentials or temporary paths. Only the fixed Stroq CLI hook is executed with isolated temporary data and a restricted environment; no agent or provider request is started. Responses require matching independent engine evaluation and verified scratch audit evidence. Captured adapter execution is separate from native-client enforcement. Unsafe or invalid history refuses new checks. See [hook checks](docs/platform/hook-checks.md).

Detector and audit projections have different retention rules from installation, backup and recovery files. Stroq does not promise that everything it writes is one-way or free of original content.

The secret index stores salted, truncated SHA-256 hashes and never a value. `stroq exposure`'s inventory stores the paths of instruction and skill files and the sha256 of their content, never the content. The decoy registry (`stroq canary --file`) stores paths; the value inside a decoy is in the secret index as a hash, like any canary. Provenance stores an excerpt of at most 120 characters, redacted structurally and against the secret values Stroq knows (in the spellings an excerpt can hold them in); the audit log runs every summary through `redact()` and the same lookup before it is appended. Both remove only what Stroq can recognise: a known value that contains a delimiter (`/`, `?`, `#`, `&`, …) and sits glued to other text such as a URL path is not found, and a credential Stroq does not know is removed only if it has a recognisable vendor shape.

**Saved platform policy checks** retain canonical action classes, exact expected effects for clean/suspect session assumptions, creation time and source incident/evidence/workspace fingerprints in `<STROQ_HOME>/console/policy-cases.json`. They retain no raw commands, transcripts, credentials, custom policy text or free-form names. The file is private but unencrypted, shared by every policy candidate using that Stroq home across workspaces, and survives restart without automatic expiry or eviction. It accepts at most 64 checks; a full, malformed or unsafe store is refused rather than replacing existing expectations. Saving reselects exact journal evidence and current policy hashes server-side. Explicit removal requires acknowledgement of the weakened regression gate and shared scope. Candidate previews bind the store revision, and apply holds its snapshot lock through the policy write. A matching class-only result does not establish original session taint, host adoption, live blocking or remediation. See [saved policy checks](docs/platform/policy-workflow.md#saved-policy-checks).

**Platform artifact reviews** persist the last explicitly reviewed sanitized capture per artifact under `<STROQ_HOME>/console/inventory-<workspace ID>.json`. V2 retains file IDs/safe labels/hashes/sizes, aggregate static capabilities, fixed rule metadata, engine/coverage fingerprints and per-entry review time; raw content, snippets, commands and environment values are excluded. Each workspace is bounded to 512 entries and 8 MiB, with no automatic expiry or eviction; an explicit later review replaces that item's prior baseline. New files are private and unencrypted. Valid v1 fingerprint-only baselines remain readable without migration; previous details stay unavailable until explicitly recorded. Compare and review bind both the selected current SHA and prior reviewed SHA. Incomplete capture or a changed analysis profile cannot silently become a clean delta. This is a local review baseline, not signed provenance, runtime behavior, trust or remediation. See [artifact review and comparison](docs/platform/artifact-review.md).

Features that install or restore files retain original bytes separately from those projections:

- **CLI artifact installation** keeps confirmed skill and MCP server files in the content-addressed `~/.stroq/store/` (or `$STROQ_HOME/store/`). These are complete stored files, not hashes alone; they may contain secrets embedded in the source. Referenced revisions are retained for comparison, restoration and rollback. Updates and removals attempt to collect unreferenced copies; failed collection leaves a warning and retained files. See the [installation and rollback guide](docs/GUIDE.md#add-a-skill-after-reading-it).
- **Platform configuration changes** back up existing hook configuration and installation-record bytes under `~/.stroq/backups/console-setup/` in the selected user home, and existing policy bytes under `<STROQ_HOME>/backups/console-policy/`. The default policy home is `~/.stroq`; browser hook setup requires that default home. Backups may include private settings or credentials already present in those files. These writers have no automatic backup expiry or eviction. Hook setup requires applicable full-copy and shared-scope consent; a raw no-op writes no configuration, record, recovery copy or lock. Unmatched registrations are preserved and ambiguous Stroq-like commands remain review-required. See [hook connection and recovery](docs/platform/agent-setup.md), the [platform guide](console/README.md#local-data-and-limits) and [policy workflow](docs/platform/policy-workflow.md).
- **Platform hook removal** retains the exact original full settings bytes as `before.json` and recovery metadata as `manifest.json` under `<selected-user-home>/.stroq/backups/console-disconnect/<receipt UUID>/`. Copies include unrelated entries and any embedded credentials. They are unencrypted, private (`0700` directories / `0600` files), have no automatic expiry or eviction, and accept at most 32 records; full or unsafe storage refuses another removal. Explicit retention and weakening consent precede a write, with separate user-wide scope consent. This POSIX/default-home writer shares the harden configuration lock with native filters. Reconnect uses current setup rather than restoring a full old file. See [hook removal and recovery](docs/platform/agent-disconnect.md).
- **Native credential file filters** reuse the CLI harden engine: ownership is recorded in `<STROQ_HOME>/harden/manifest.json`, and source copies are retained under `<STROQ_HOME>/backups/`. Copies can contain complete private settings or embedded credentials. The engine avoids copying credential-shaped source text and then uses surgical undo; detection can miss embedded secrets. Copy retention is the first plus newest four per file on a best-effort basis, without automatic expiry, including after undo. No-op apply creates no copy or ownership. The manifest (`stroq harden` and these filters alike) is version 2 and signed: an HMAC-SHA256 under the home's state key `<STROQ_HOME>/keys/state-mac.key` (32 random bytes, mode 0600, made by the first writer) over what it records, including the SHA-256 of each copy it points to. `stroq harden undo`, `apply` and `status` refuse, and write nothing, when the manifest does not match its signature, when the key is missing or not private, or when a copy undo would restore is there but is not the recorded bytes (a copy that is gone still falls back to surgical undo). A version 1 manifest from before signing is refused too: move it aside and run `stroq harden apply` again; what earlier applies added stays in the files, and undo will not take it out, so remove it by hand if you want it gone. This is tamper-evident, not a boundary: a process running as the same user that can read `keys/`, or write a key of its own there, can still sign, and one that kept an older manifest this home signed can put it back (undo still restores a copy only when the file is exactly as that apply left it). `stroq run --sandbox` write-protects `keys/`, `harden/` and `backups/`. See [file filters and recovery](docs/platform/credential-filters.md).
- **Platform skill quarantine** retains the original files at `<project-or-user-home>/.claude/.stroq-quarantine/<record UUID>/payload`. It preserves any secrets in those files and keeps the payload after restore. There is no automatic garbage collection or payload deletion; a full vault refuses another operation. The project vault stays in that project, while the user vault is shared across its workspaces. See [quarantine storage and limits](docs/platform/skill-quarantine.md#storage-and-limits).
- **Platform MCP registration containment and proxy configuration** retain the complete original configuration (`before.json`), the edited configuration (`changed.json` for v2; legacy v1 removals keep `removed.json`) and private recovery metadata under `<selected-user-home>/.stroq/console/mcp-containment/<record UUID>/`. Reads do not migrate legacy recovery files. These files include unrelated entries and any credentials, headers or environment values present in either configuration, including server-owned policy/profile environment added to a proxy entry. They are **unencrypted**, remain after restore and have no automatic expiry or garbage collection. The shared user store accepts at most 32 records and 17 MiB of accounted payload/metadata across both actions; each configuration payload is limited to 256 KiB. Vault/record directories must be owned by the current user with mode `0700`, and retained files must be owned with mode `0600`; unsafe retained state is refused. This location stays under the selected user home even when the server uses a custom `STROQ_HOME`. Mutations require explicit acknowledgement of retention and active-session limits. See [MCP storage and recovery](docs/platform/mcp-containment.md#storage-and-recovery).

These retained files are **unencrypted**. New CLI store files and platform backups use mode `0600` inside directories created with mode `0700` on POSIX. Quarantine checks private vault/record directories and metadata, while the moved payload retains its original file modes beneath them. MCP containment checks its private recovery directories/files and does not support Windows mutation. These permissions do not protect data from another process running as the same OS user, and recovery storage is not an execution sandbox. Portable identity checks and atomic rename do not provide filesystem compare-and-swap against a malicious local writer. Detector/audit redaction does not redact original artifact or backup bytes. The [Windows permission limits](#windows) below also apply to features that support that platform.

## The cloak dictionary (`~/.stroq/cloak/`)

**`stroq mcp --cloak` retains a reversible value dictionary, and you should decide about it deliberately.** It replaces values in an MCP server's `tools/call` results with placeholders before the model reads them, and restores them on the way back to that server — which means it keeps a dictionary that maps a placeholder to the real value, in the clear, on disk. It is separate from the original artifact and recovery files described above.

Its rules:

- It exists **only** if you passed `--cloak`. Without the flag there is no dictionary and nothing to read.
- It lives in `~/.stroq/cloak/` (or `$STROQ_HOME/cloak/`), **never** in `secrets.json` — a separate directory so the reversible store cannot be confused with the one-way ones, and so `rm -rf ~/.stroq/cloak` deletes every one of them in a single command.
- Mode `0600`, inside a `0700` directory, written through a temporary file and a rename.
- One file per **(session, server)** pair, named by a truncated `sha256` of the pair, so the filename gives away neither. A placeholder minted from server A's data can therefore never be restored into a call to server B: B's dictionary has never heard of it, so the literal placeholder text travels instead.
- An entry is forgotten **12 idle hours** after it was last minted or used, and a dictionary holds at most 2000 entries, least recently used dropped first. Both prunings are applied on the next read, so an abandoned dictionary decays without anything having to run.
- A value it forgot, or a dictionary it cannot parse, means a placeholder is forwarded to the server as literal text. It never means a wrong value is restored.
- The value is **never** written to the audit log. A cloak entry there carries the direction, the kind, the placeholder and a count, and has no field that could hold a value.

A placeholder standing for the value of a **known secret** — anything in the secret index — is never restored at all. The call carrying it is denied (`mcp-cloak-secret-restore`), because the model only ever saw the placeholder and restoring it would be Stroq itself sending a credential to a third party.

Making the cloak restore a value it should not, leak a value into the audit log or the proxy's own stderr, resolve a placeholder across servers, or forward an uncloaked result while claiming to have cloaked it, is **in scope** and wanted. So is any way to make a dictionary outlive its TTL or be written with wider permissions.

## Windows

Stroq's CI runs its suite on Windows, but with less behind the promises above than on macOS and Linux.

- **File permissions.** `0600` and `0700` are POSIX modes, and Windows does not apply them. The index, the audit log, the cloak dictionary and the rest of `~/.stroq` are protected by the ACL of the user profile they live in, which by default admits the user, SYSTEM and Administrators. A `STROQ_HOME` outside the profile gets whatever that directory grants.
- **The Claude Code plugin's hook** is a POSIX shell script, so on Windows it needs a shell that can run one, such as Git Bash; whether Claude Code runs it that way has not been verified. `stroq init`, which writes the hook into `.claude/settings.json` directly, does not depend on it.
- **The hook line.** A host that hands the line to `cmd.exe` with each quote escaped (Antigravity does) cannot start a line that has a quote in it, and Antigravity refuses every tool call while its hook cannot start. For Antigravity, Cursor and Codex `init` writes the line with the paths bare (8.3 names for a blank) and starts it the way such a host does before it keeps it; it writes nothing for Antigravity when no spelling starts. The program in the line is always a path: `cmd.exe` looks for a bare `node` in the current directory first, and the current directory of a hook is the project's, which a cloned repository can fill. Claude Code, Copilot and Windsurf keep the quoted line, which their hosts read (Git Bash, PowerShell's `&`). None of the five has been run on Windows by the author; the tests that start the lines with the real `cmd.exe` run on the Windows job of CI.
- **`stroq run --sandbox`** relies on srt, whose Windows support is an alpha; the generated config is checked on macOS and Linux only.
- **OpenClaw:** `stroq init --agent openclaw` finds `openclaw.cmd` on `PATH` but prints the two install commands instead of running them, because a `.cmd` shim only runs through a shell that would re-split the plugin path.

## Scope

**In scope:** any way to defeat a protection this project documents as working today for the Claude Code, Cursor, Codex, Copilot CLI, OpenClaw, Windsurf or Antigravity adapter, or for the MCP stdio proxy. For example: a `shell.network`, `shell.exec_encoded`, `git.push_external`, `fs.secrets`, or `config.self` action that the README or `policies/default.yaml` says should be denied or asked, but is instead silently allowed; or content that should trip a rule in `rules/stroq/` (or a non-disabled rule in `rules/atr/`) but is normalized and scanned as clean.

**Writes to instruction and memory files** (`config.instructions`) are in scope on their own terms: a write to one of the files `docs/GUIDE.md` lists that a tainted session makes without being asked, or a write whose own text trips a rule and is not asked about, is a bypass. Known limits: a patch (Codex's and Copilot's `apply_patch`, or `git apply` of a diff file) reaches Stroq as file paths only, or with its targets inside the diff, so its text is never scanned and only the taint decides; a file name built at run time (`$(…)`, `eval`, a variable set by anything but a plain `NAME=value` in the same command) is not resolved; a file an agent loads as instructions that is not on that list is not covered; and the agent's own, built-in memory feature — one that saves outside the files — is invisible to hooks.

**Writes that install something a trusted process runs later** (`config.persistence`) are in scope on their own terms: a write to a shell startup file, an SSH `authorized_keys` or `rc`, a LaunchAgent or user systemd unit, a scheduled job, or an editor task that runs on opening the folder, which the default policy asks about and, in a tainted session, denies; the same write reached through a symlink a file tool or an MCP file tool names; the text of a write that makes a git config, an MCP server list or an agent definition run a program; and a shell script on disk whose contents do what the command line does not say. Known limits: only shell-family scripts are read (a Python or Node program is not), one level deep; a file the same command line downloads, writes, copies, moves or links is judged by where its text comes from, and one it may have made that is not on disk yet is asked about; what a script computes at run time is not followed; a file copied into place by a later tool call is not read; a link followed inside a Bash command that the same line did not make is not resolved; git configuration is read only in files named like one (`config`, `*gitconfig*`, `.cfg`, `.conf`, `.ini`, `.inc`); an npm lifecycle script, a swapped virtualenv interpreter (one in a folder the same line unpacks or clones into is asked about), `docker run --privileged` and a socket escape, and `sudo systemsetup -setremotelogin on` are not recognised; and a tool call forged inside a model response is invisible to hooks. A project MCP config (`.mcp.json`, `.cursor/mcp.json`) is not denied as self-tamper, because adding a server is routine; it is asked about in a tainted session, or when the text written registers a shell or an inline interpreter as the server.

**Out of scope (known gaps, already on the roadmap — please still report if unsure, but expect these to be closed as duplicates of tracked work rather than triaged as new):**

- Evasions of the shell classifier that rely on a construct it does not read. It is a reading of shell text, not a shell, and says what it is not sure it read (`shell.unparsed`) rather than guessing. Known: a command word made at run time from something other than a literal (`$(cat name.txt) -rf ~`, `${x:-rm} -rf ~`, an array or `set --` that holds it; a substitution that only prints a literal, `$(echo rm) -rf ~`, is read, and so is a wildcard in the path of a command, `/bin/r[m] -rf ~`), a variable that a shell runs as a command (`PROMPT_COMMAND=… bash -i`, `PS4='$(…)' bash -x`; setting one with a substitution in it is asked about, what it then runs is not followed), a command word that a variable made out of a transformation Stroq has no name for, in a command that fetches nothing (`x=$(… | rev); $x`; a command word that a substitution makes is asked about), text that a fetch wrote to a file or a pipe that another tool call reads (in one command line `curl -o f … && sh f` is denied as `curl … | sh` and `mkfifo p; curl … > p & sh < p` is asked about; across two tool calls a fetched file is read from disk without knowing it was fetched), and a program written inside an interpreter's string (`perl -e 'system(…)'`, `awk 'BEGIN{system(…)}'`, `fs.rmSync`; only those that name `child_process` or `subprocess` are read, and an inline `python -c` program's literal process commands, such as `os.system('…')`, are read as commands of the line) or in a Makefile that `make` is handed through `<(…)` or `-f -`, which are not read; a script handed to a shell by a name an expansion makes and the command did not set (`bash "$f"`, `bash $(find . -name x.sh)`), which is not read (a program the shell is _piped_ or _given_ under such a name is asked about); a script run by a path with a pattern in it rather than handed to a shell (`./tool.s?`) and zsh's own pattern forms that hold no wildcard (`bash (x|y).sh`), which are not read; the commands of a script inside a script, which are read one level deep; the functions that a script defines and calls, which are not followed (a script is read as a bag of lines, a line once for each value its variables take, and no function in it ends where it should), and the anonymous function of zsh (`() { …; } -rf ~`), while those of a command are, where they are called, in a substitution, an `eval`, a `trap`, the command that `ssh` sends and a shell that was given them by `export -f`, and a call that cannot be put in place is asked about; zsh's short form of a loop (`for i (a b) cmd`) and an option that makes another program run a command (`tar --to-command`, `rsync -e`, `gdb -ex 'shell …'`, `LESSOPEN`), which are not read, beside the ones that are (`find -exec`, `xargs`, `watch`, `parallel`, `su -c`, `script -c`, `entr -s`, `npx -c`, the `!` of an editor, `fd -x`, `rg --pre`, `nodemon --exec`, `tmux new-session -d '…'` and the `#(…)` of its format strings, `screen -dmS name …`, `concurrently '…'`, `osascript -e 'do shell script "…"'` and its JavaScript form, `nix-shell --run`, a shell that `su`, `runuser` or `newgrp` starts for another user, which reads what it is given); a program that runs another command and that Stroq has no name for (a launcher of your own, a tool that is not on its list of those that run a command) hides what it runs from the readers that look at the first word of a stage, as an option of a known one that takes a value does where it is not in its table (the wrappers `sudo`, `env`, `flock`, `chrt`, `taskset`, `strace`, `unshare`, `nsenter`, `systemd-run`, `runuser`, `direnv exec`, `mise exec`, `uv run` and the like are known, with the options of each that take a value; a package runner's option that is not known is read as one that may take one); shells whose syntax is not POSIX's (fish, csh), which are read as the same text; and a command too costly to read in the time a host waits, which is asked about and not read, as is one whose reading goes on for eight seconds (`reading-took-too-long`: the clock is checked where a text is taken apart, and a single step that is itself slow, one pattern that backtracks, is not interrupted by it). A way to run a program that the reading neither decoded nor asked about is in scope. The reading of a fetch piped into an interpreter rests on a list of names that cannot run code (`packages/core/src/actions/inline-python.ts`), checked against the Python of the machine that runs the tests: a way to run code with names on the list, on a Python the tests were not run on, is a bypass and in scope, and so is a here-document body that is read as text when something runs it (an editor that reads it, a command that is not the one its name says), and an `eval` of a tool on the list of tools that print their own setup (`packages/core/src/actions/init-tools.ts`) that is passed when what it prints is not that; an inline Node, Perl, Ruby or PHP program is not read (Node is asked about, the others are a stop as they were).
- An action that follows a flag on the developer's own text without copying from it. A flag on a file of the project read with `Read` or `Grep`, or on what a local command printed, does not taint the session by design (most such flags were false, and a taint stops the network and secrets for the rest of the session): what is copied from that text is asked about, and so is a call that reads secrets and sends something out in the same call. An instruction in the project's own files that the agent follows in its own words, in two calls (a secret read, then a send that does not carry its value), is that design, not a bypass. A copied action that is not asked about, a secret-and-send call that is not asked about, or a flag on somebody else's text that does not taint, is in scope: a page, an MCP result, an instruction file, a dependency's files, a file the session downloaded, and the output of any command that runs a program outside the list of local programs `packages/core/src/scan/local-commands.ts` keeps. A program on that list that prints text from elsewhere is in scope too.
- Denial of a single scan via a pathological regex running past the build-time performance gate: worker-isolated scanning (so one slow match cannot stall the hook process) has not shipped yet; today the gate only rejects rules that are already slow against the fixed benchmark blobs.
- Adapters for any agent other than Claude Code, Cursor, Codex, Copilot CLI, OpenClaw, Windsurf and Antigravity — there are none, so there is nothing to bypass. The MCP stdio proxy covers any client that launches stdio MCP servers, and is in scope on its own terms below.
- The OpenClaw limits [docs/AGENTS.md](docs/AGENTS.md#openclaw) documents: `after_tool_call` is an observe hook, so a suspect result taints the session but no warning reaches the model, and a report that the model was not warned is a v1 scope cut rather than a bypass (the taint being _ignored_ on the next call is a bypass and is in scope); `requireApproval` needs an approval route, and an unanswered prompt becomes a block, not an allow; MCP tool names are not documented for OpenClaw, so every non-native tool — `message`, `browser`, `process`, `code_execution` and anything unknown — is classified as `mcp__openclaw__<tool>` and no rule can be keyed on an OpenClaw MCP _server_; the plugin blocks the call on a missing binary, a spawn error, a non-zero exit, a timeout or an unreadable answer, so a report that Stroq can be made to _fail_ is a reliability issue unless it also shows the call being allowed; a `pre` on a read-shaped tool (`read`, `web_search`, `x_search`, `ask_user` and the other pass-through tools) answers an internal error with `allow`; a call whose command, patch, path or URL Stroq cannot read is denied with `openclaw-unreadable-input` and one naming more than 64 files or URLs with `openclaw-too-many-targets`; and no tool's `params.cwd` — `exec` included — ever changes which directory feeds the secret index or the path rules, since every call is judged against the plugin's configured `workspace`, or the Gateway's own directory when that is unset. An action that gets through `before_tool_call` — including one hidden behind a forged `*** Add File:` line, a hostile tool name, a `params` field spelling Stroq neither reads nor denies, a shell spelling outside `exec`/`bash`/`sh`/`zsh`/`shell`/`exec_command`/`local_shell`/`run_command`/`terminal`, or a `params.cwd` that manages to redirect the secret index for any tool — is in scope, as is anything that makes the plugin return an allow it did not get from the CLI. The OpenClaw wire format is inferred from its documentation and one production plugin rather than recorded from a real session, so a payload shape that reaches the engine as an empty action is exactly the kind of report that is wanted.
- The Windsurf limits [docs/AGENTS.md](docs/AGENTS.md#windsurf) documents: Cascade hooks have no `ask`, so every policy `ask` is enforced as a block whose reason says a prompt was not possible and names the rule to relax; `post_run_command` carries the command line and working directory only, so a poisoned command OUTPUT cannot taint a Windsurf session and a report that it does not is a v1 scope cut rather than a bypass (a file read or an MCP result that fails to taint IS a bypass and is in scope); web pages Cascade fetches have no hook event at all; any exit other than 0 or 2 is treated as an allow by Windsurf, so Stroq answers its own internal errors with exit 2 on `pre_run_command`, `pre_write_code` and `pre_mcp_tool_use` and with silence on `pre_read_code`, on every `post_*` event and on an event it did not install on; there is no hook timeout setting and the docs do not say what a hung hook does, so a report that Stroq can be made to run SLOWLY is a performance issue unless it also shows Stroq answering incorrectly; a `post_read_code` reads at most 1 MiB of the named file and scans nothing for a directory, a missing file or an empty one, so a poisoned file inside a directory Cascade read recursively does not taint the session (the file itself, read individually, still does); `tool_info.cwd` never changes which directory feeds the secret index or the path rules, since every call is judged against the hook's own working directory; a `pre_write_code` or `pre_run_command` whose non-empty `tool_info` yields no path or command is denied with `windsurf-unreadable-input`, and one naming more than 64 files with `windsurf-too-many-targets`; - The Antigravity limits [docs/AGENTS.md](docs/AGENTS.md#google-antigravity) documents: no tool result reaches `PostToolUse`, so the output of a command or an MCP call is never scanned (a file is re-read by its path instead), and the adapter has been checked against documented payloads, not a live Antigravity session.
- The MCP proxy limits [docs/AGENTS.md](docs/AGENTS.md#mcp-proxy-any-mcp-client) documents: an MCP proxy has no channel to a human, so every policy `ask` is enforced as a blocked tool result naming the rule to relax; only stdio servers are wrapped, so an HTTP (`url`/`serverUrl`) entry is skipped by `init` and is not protected, and VS Code's and Codex's config shapes are not rewritten in v1; results delivered outside the `tools/call` response — the tasks extension, resource subscriptions, and sampling or elicitation payloads inside legacy server-initiated requests — are not scanned, and a report that one of those is unscanned is a v1 scope cut rather than a bypass; a JSON-RPC batch containing a `tools/call` is refused whole (`mcp-proxy-batch`) and a `tools/call` with no string `params.name` is denied (`mcp-proxy-malformed-call`), both fail-closed; a `tools/call` whose request id cannot be classified as a valid JSON-RPC id is dropped and audited (`mcp-proxy-unaddressable-call`) rather than forwarded with no way to address a reply to it; a client line that is not valid JSON — after a leading byte-order mark is stripped — is otherwise forwarded unchanged, unless its text names `tools/call` (matched case-insensitively), in which case it is dropped and audited (`mcp-proxy-unparseable-call`) rather than forwarded unread; a `tools/call` whose arguments serialise past 2 MiB — everything core's secret-egress guard scans — is denied fail-closed (`mcp-proxy-arguments-too-large`) and never forwarded, since a call Stroq can scan only a prefix of is a call padding defeats; a throw while judging a `tools/call` is a deny (`mcp-proxy-internal-error`) and never forwarded, while a throw while scanning a result forwards the result and logs when cloak is off; with cloak on, the result is still masked before delivery; a client line is always parsed however large, but a SERVER line above 8 MiB is forwarded unparsed, unscanned and untainted, so a server that pads a poisoned result past that size keeps it out of the scan entirely — a documented limit and a v1 scope cut rather than a bypass; the project directory is the one `init` recorded in `--cwd` and nothing on the wire changes it, nor the session, which is `mcp:<client>` and therefore shared across a client's conversations (a taint that persists between chats is by design; `stroq untaint --session mcp:<client>` clears it); an upgrade or uninstall that moves or removes the recorded entry path without `init` being re-run leaves a stale wrapper, which `stroq doctor` reports rather than counting as protected, and which `stroq init --agent mcp` repairs by replacing it on the next run; and `.mcp.json` and `.cursor/mcp.json` are deliberately NOT self-tamper protected, since adding an MCP server to a project config is routine agent work — the two user-level client configs, `claude_desktop_config.json` and `mcp_config.json`, are protected, and a content-aware check that protects only the wrapped entries is tracked as the follow-up. A `tools/call` that gets through the proxy — including one hidden behind a hostile server or tool name, a field spelling Stroq neither reads nor denies, or a framing trick that makes a judged line reach the server unjudged — is in scope, as is any way to make the proxy forward a call the engine denied, or to make it read the server name, the session or the policy directory from the wire. The MCP wire handling is built from the specification and three open-source proxies rather than recorded from a real client, so a message shape that reaches the engine as an empty action is exactly the kind of report that is wanted.
- The `--strict` limits [docs/AGENTS.md](docs/AGENTS.md#--strict-nothing-reaches-the-client-that-stroq-could-not-read) documents (the flag is off unless you passed it; without it none of this applies, and the default proxy still forwards what it could not read, as the MCP limits above say): strict mode is a filter on what the client receives, not a sandbox for the server, and withholding a message cannot undo what the server already did; a delivered message was read in full by the same rules the default scan uses, which is not a promise it is safe, and a picture or sound that passes the media check is delivered unread; a result above 200,000 characters of text, an image above 8 MiB on the wire, and any server that sends more than a few messages of its own are withheld or counted (the server is ended past 20 malformed or hostile messages, or 1000 messages of kinds a benign server also produces, forwarded or withheld), by design; a server batch is withheld whole, answering the pending ids it carries; a response that cannot be associated reliably with a waiting request fails the pending requests on that wrapper with fixed errors (including unrelated concurrent requests), rather than leaving them waiting; strict mode scans, as one of its texts, exactly the text the default proxy scans (the same reader), so by construction it reads at least what the default does, plus aggregate decoded strings, a per-string view for each distinct decoded string, and the result as JSON (the first 200,000 characters of it, so a rule written for JSON can miss a payload beyond that in a very large result); each text of a result is scanned twice, the first time with all of them under one hard 4-second deadline, so the bound is a measured cost rather than a proof; and delivered messages are re-written as the JSON Stroq parsed. Making a strict proxy deliver a message it did not scan, deliver a field it does not read, forward a server-initiated method that is not one of the five documented, leave a tracked request unanswered after withholding its answer, write the server's own words into the client's error or the audit, or make the dry-run SCAN of a message run past its 4-second hard deadline, is IN SCOPE. The deadline bounds that dry-run scan only: the time the proxy spends parsing, reading and serialising a large message, and in the engine's own scans that follow the dry run, is outside it (an 8 MB clean result blocked one wrapper's event loop for 1.6 to 6 seconds in review measurements before per-string views were added, about 10 seconds cold), which is an availability effect on that wrapper and is reported as a performance issue, not as a bypass. Also known and documented: a `stroq trust` entry suppresses only the one view of a result whose text it was made from; ending the server signals the detached process group on POSIX, including escalation after the leader exits; end-anchored rules are scanned per decoded string under `--strict`, while trailing fields still affect the default proxy; JSON-specific rules read only the first 200,000 characters of the JSON view, and the default proxy clips its own text to that window; a Stroq without `--strict` cannot start a strict wrapper and its `init --agent mcp` re-run drops the flag silently (mixed versions only); and the dry run uses the bundled rules, not an embedder's own rule set.
- The `--cloak` limits [the guide](docs/GUIDE.md#guarantees-and-limits) documents (the flag is off unless you passed it; without it none of this applies): only `tools/call` RESULTS are cloaked, so a `tools/list`, a `resources/read` and a `prompts/get` reach the model with their values intact and a report that they do is a v1 scope cut; person names and street addresses in labelled fields are detected and repeated mentions in the same result are replaced, but unlabelled prose and EIN in the `NN-NNNNNNN` form remain outside the cloak; object keys are never rewritten (a secret placeholder in one still refuses the call); a result above 8 MiB, or above 2 MiB once parsed, is DROPPED rather than forwarded, so the client's request for it goes unanswered; a placeholder the dictionary no longer knows is forwarded to the server as literal text; a placeholder standing for a known secret is never restored and the call carrying it is denied (`mcp-cloak-secret-restore`); a cloaked result and a restored call are re-serialised, so only those two message kinds stop being forwarded byte for byte; and a model that paraphrases a placeholder instead of echoing it verbatim simply loses the link. Making the cloak restore a value it should not, resolve a placeholder minted for a different server, write a value into the audit log or the proxy's own stderr, or forward a result it did not cloak while the audit says it did, is IN SCOPE. So is a detected kind that turns out to carry action classification — restored arguments are judged before forwarding, so a path or command recovered from a placeholder must receive the same policy decision as its literal form.
- The secret-egress guard's own bound: an outbound action's arguments are scanned whole in overlapping 256 KiB windows up to 2 MiB, and an egress-shaped action above that bound is denied as `secret.unscannable` rather than forwarded half-scanned — for every adapter, not only the MCP proxy, which is what closes the padding bypass the 2026-09-08 review found. Making a known secret value leave inside those 2 MiB IS in scope, and so is any way to make an over-2-MiB egress action be allowed. Outside it: `WebFetch` contributes its `url` and `prompt` only, so a credential placed in a header it sends is a pre-existing gap; the post-scan of tool results keeps its own 200 000-character clip, so a poisoned result padded past that is not scanned beyond the clip; and a legitimate inline payload above 2 MiB being refused is the documented trade-off, not a bug.

The Copilot wire format is inferred from GitHub's documentation rather than recorded from a real session, so a payload shape that reaches the engine as an empty action is exactly the kind of report that is wanted.
