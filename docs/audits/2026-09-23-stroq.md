# Stroq: аудит защиты и план улучшений

**Срез:** commit `7a0b6c850984716fbf78d970f1127ab5213dd119`, версия 0.15.2, 23 сентября 2026 г. Локальная среда: macOS/Darwin arm64, Node.js 24.13.1, pnpm 11.24.0. Проверки выполнялись на этом commit; изменения исходников в аудит не входили. Воспроизведения использовали только синтетические данные и временные каталоги ОС.

**Последующая реализация:** описанные ниже находки относятся к указанному исходному commit. После аудита в текущем рабочем дереве внесены исправления A-01–A-14 и регрессионные тесты. Итоги повторных проверок и оставшиеся ограничения приведены в конце документа; это не меняет доказательства и приоритеты исходного среза.

## Вывод

Текущий набор тестов и сценариев проходит, но есть **восемь подтверждённых дефектов защиты/диагностики с приоритетом P1**, которые он не покрывает. Наиболее существенны пропуск закодированного payload после 50 base64-токенов, неполная классификация файловых MCP-вызовов, проверка маскированного MCP-аргумента до его восстановления и запись известного секрета в audit log. Перед следующим релизом следует закрыть эти случаи и добавить независимые регрессионные сценарии. Приоритет здесь отражает последствия в заявленной модели угроз, а не доказательство эксплуатации на машине пользователя.

P1 означает, что заявленная защита может пропустить действие, раскрыть значение или ошибочно объявить установку работающей; P2 — нарушение корректности/устойчивости или существенная ложная блокировка; P3 — документация и удобство. «Высокая уверенность» означает воспроизведение на коде проекта; это не означает проверку на каждой версии внешнего агента. Оценки S/M/L: изменение на часы / несколько дней / работа через несколько подсистем.

## Охват и механизм

Просмотрены точка входа CLI, движок, нормализация, правила, политики и классификаторы, индекс секретов, taint/provenance/trust, локальные хранилища и аудит, семь адаптеров, MCP-прокси и cloak, установка и диагностика хуков, запуск с sandbox, тесты/bench/coverage, пакет, CI/release, README/SECURITY и сайт. Проверены пути `PostToolUse → scan → taint/provenance → PreToolUse → classify → policy → audit`; для MCP отдельно проверен порядок `judge → restore → forward` и обработка ошибки на ответе. Полный перебор всех комбинаций внешних агентов, ОС и MCP-серверов невозможен без их реальных wire payload; такие места указаны ниже.

| Интеграция | Проверяемый до действия канал | Результат и существенная граница |
| --- | --- | --- |
| Claude Code | `PreToolUse`: shell, запись/правка, чтение, WebFetch, MCP | `PostToolUse` сканирует результат; подозрительный ответ уже прочитан агентом. Настоящий `ask` доступен. |
| Cursor | `beforeShellExecution`, `beforeMCPExecution`, `beforeReadFile` | Вывод shell/MCP сканируется позже; `afterFileEdit` лишь аудирует правку. Общий блокирующий `preToolUse` пока не установлен. |
| Codex | `PreToolUse`: shell, patch, MCP | `PostToolUse` сканирует доступный вывод; `ask` превращается в deny. Собственный web-канал хук не видит. |
| Copilot CLI | `preToolUse` для всех инструментов | `postToolUse` сканирует результат; хост пропускает вызов при таймауте хука. |
| OpenClaw | Плагин `before_tool_call` | `after_tool_call` наблюдает результат, но не заменяет уже полученный моделью ответ. |
| Windsurf | Pre read/write/command/MCP | Post read/MCP доступны; вывод shell и собственный web-контент хук не получает. |
| Antigravity | `PreToolUse`, `PreInvocation` | Post повторно читает файл; вывод command/MCP недоступен. Реальный агент не тестировался. |
| MCP stdio-прокси | `tools/call` до сервера | Результаты `tools/call`, `tools/list`, `resources/read`, `prompts/get` сканируются; cloak применяется только к результату `tools/call`. `ask` возвращается как отказ. |

Матрица составлена по установщикам и обработчикам проекта и сверена с первичными описаниями [Claude Code](https://code.claude.com/docs/en/hooks), [Cursor](https://prod.cursor.com/docs/hooks), [Copilot CLI](https://docs.github.com/en/copilot/reference/hooks-reference), [Windsurf](https://docs.windsurf.com/windsurf/cascade/hooks) и [MCP](https://modelcontextprotocol.io/specification/2025-11-25/server/tools). Договоры внешних хостов меняются; для Codex, Copilot, Windsurf, OpenClaw и Antigravity нужны сохранённые реальные входные/выходные события, прежде чем считать совместимость доказанной.

## Подтверждённые находки

### A-01 · P1 · Высокая · M — лимит декодирования скрывает инъекцию

**Условие и наблюдение.** В [normalizer.ts](../../packages/core/src/normalize/normalizer.ts#L85) и [decodeLayer](../../packages/core/src/normalize/normalizer.ts#L202) берутся только первые 50 base64-токенов каждого слоя. Один закодированный текст с инструкцией отдельно даёт `suspect`, а после 50 безвредных токенов (~2 КБ) — `clean`, score 0; весь текст намного короче общего предела 200 000 символов. Тем же `expandVariants` пользуется извлечение provenance, поэтому связь с предложенным действием тоже может потеряться. Ожидалось обнаружение или явное fail-closed решение о превышении лимита. **Влияние:** обфускация инструкции проходит без taint и provenance. **Исправление:** лимитировать трудоёмкость, но никогда не возвращать `clean`, если кандидаты остались непроверенными; при исчерпании бюджета выдавать отдельный подозрительный/непроверенный результат. **Приёмка:** 51-й и более поздние кандидаты с вредным текстом обнаруживаются либо помечаются как непроверенные, а benign-корпус и 4-секундный бюджет остаются измеряемыми.

### A-02 · P1 · Высокая · M — MCP-файловые вызовы обходят классы путей

**Условие и наблюдение.** [Классификация MCP](../../packages/core/src/actions/classify-tool.ts#L118) ищет `config.self` по сырому аргументу и не присваивает `config.git_exec` или `fs.secrets`. Синтетические вызовы `write_file(path: '.claude/settings.json')` → deny; `write_file(path: '.claude/./settings.json')` и `write_file(path: '.claude/x/../settings.json')` → allow. Запись `.git/hooks/pre-commit` через MCP также даёт allow, хотя нативная запись блокируется. `read_file(path: '.env')` под taint не получает класс секретного файла. Ожидались одинаковые решения для одинакового файлового действия независимо от транспорта. **Влияние:** обход постоянной защиты конфигурации/Git hooks и чтение секретного файла в tainted-сессии через файловый MCP-сервер. **Исправление:** нормализовать значения path-like аргументов тем же способом, что нативные файловые инструменты; для распознанных файловых MCP-инструментов присваивать read/write и соответствующие классы пути. Не считать все произвольные MCP-тексты путями. **Приёмка:** нативные и MCP-варианты `.claude`, `.git/hooks` и `.env` дают соответствующие решения; обычный текстовый аргумент с упоминанием пути не блокируется. Возможны новые блокировки файловых MCP-вызовов.

### A-03 · P1 · Высокая · M — cloak восстанавливает аргумент после решения

**Условие и наблюдение.** [proxy-pump.ts](../../packages/cli/src/mcp/proxy-pump.ts#L264) вызывает `judgeToolCall` для placeholder, а [forwardWithRestores](../../packages/cli/src/mcp/proxy-pump.ts#L188) затем подставляет исходное значение и отправляет его серверу. На синтетическом стенде прямой `write_file(path: '.claude/settings.json')` был остановлен `deny-self-tamper`; запись того же пути как значения `first_name` в результате сервера получила `[STROQ_NAME_1]`, и следующий `write_file(path: '[STROQ_NAME_1]')` был разрешён и отправлен серверу с восстановленным защищённым путём. Имя поля распознаётся в [keyed.ts](../../packages/core/src/cloak/keyed.ts#L38); нельзя полагаться на то, что восстановимое значение «не влияет на классификацию». **Влияние:** MCP-сервер может вложить управляемое значение в маскируемое поле и обойти политику на обратном пути. **Исправление:** перед отправкой повторно классифицировать полностью восстановленные аргументы тем же движком; сохранить специальный запрет восстановления известного секрета. **Приёмка:** вызов с placeholder и восстановленным защищённым путём блокируется так же, как прямой вызов, а обычные имена/адреса по-прежнему восстанавливаются. Следует учесть вторую запись аудита или обозначить в ней исходный и восстановленный этап без раскрытия значения.

### A-04 · P1 · Высокая · S/M — известный секрет сохраняется в аудите

**Условие и наблюдение.** [Проверка индекса](../../packages/core/src/engine.ts#L285) выполняется только для исходящих классов; [pre](../../packages/core/src/engine.ts#L338) и [post](../../packages/core/src/engine.ts#L392) передают summary в аудит. Эвристика [redact](../../packages/core/src/audit/audit-log.ts#L141) не скрыла синтетическое 18-символьное значение из `.env` в локальной команде `printf`: оно оказалось в обеих постоянных записях, хотя вызов был `allow` и не был сетевым. Ожидалось, что известное секретное значение не попадёт в audit log ни для одного класса действия. **Влияние:** дополнительная копия секрета в долговечном локальном логе (доступ к нему ограничен правами файла, но это не устраняет дефект). **Исправление:** отделить проверку на секрет для редактирования summary от решения `secret.egress`; индексировать/редактировать известные значения во всех audit-путях или заменять потенциально чувствительный аргумент безопасным описанием. **Приёмка:** синтетический секрет не встречается в `pre`/`post` записи для shell, файла, web и MCP; лог сохраняет имена правила и источника без значения. Формат записи можно оставить прежним.

### A-05 · P1 · Высокая · S/M — ошибка post-сканирования раскрывает ответ при cloak

**Условие и наблюдение.** При исключении из `scanMcpResult` [proxy-pump.ts](../../packages/cli/src/mcp/proxy-pump.ts#L359) сразу пересылает исходный ответ. На синтетическом pending `tools/call` повреждённое состояние сессии вызвало исключение; email из результата дошёл до клиента как есть, а cloak не запускался. Ожидалось выполнение обещанной маскировки или отказ в доставке результата. **Влияние:** при сбое сканирования именно чувствительный результат может попасть модели. Это поведение упомянуто в SECURITY как ограничение post-сканирования, но его сочетание с `--cloak` является существенным риском приватности. **Исправление:** развести обработку ошибок сканирования и маскировки; при включённом cloak маскировать независимо от scan-ошибки, а если это невозможно — не доставлять исходный результат и отдавать адресуемую ошибку клиенту. **Приёмка:** forced `engine.post` failure с email не выдаёт сырой email клиенту; без cloak сохраняется документированный observe-only режим.

### A-06 · P1 · Высокая · M — неполный hook считается защитой

**Условие и наблюдение.** [doctor](../../packages/cli/src/commands/doctor.ts#L73), [Cursor check](../../packages/cli/src/commands/doctor.ts#L89) и [Codex check](../../packages/cli/src/commands/codex-hooks.ts#L176) ищут любую команду Stroq среди всех событий. Синтетические конфигурации только с `PostToolUse` (Codex/Claude) или `afterFileEdit` (Cursor) дают `installed: true`; [preflight запуска](../../packages/cli/src/run/preflight.ts#L68) проверяет именно этот статус. Наличие прежней команды в сохранённой конфигурации может пройти и проверку install record. Ожидалось требование всех блокирующих pre-событий с правильными matchers/flags. **Влияние:** `doctor`, `exposure` и `stroq run` могут сообщать о защите и запускать агента без действующего блокирующего хука. **Исправление:** для каждого агента проверять обязательный набор событий, command, matcher и fail-closed параметры, показывать недостающие элементы по имени. **Приёмка:** post-only/неверное событие/неполный matcher показывают `not installed` или degraded и вызывают отказ `stroq run`; полная конфигурация проходит. Возможна смена текста вывода и машинного статуса команд.

### A-07 · P1 · Высокая · M — Grep по секретному файлу не классифицируется

**Условие и наблюдение.** [classifyTool](../../packages/core/src/actions/classify-tool.ts#L152) обрабатывает `Read`, но для `Grep{path: '.env'}` возвращает пустой набор классов. Copilot (`grep`/`rg`) и Antigravity (`search_directory`/`grep_search`) передают такие вызовы через pre-hook; политика `deny-secrets-when-tainted` не срабатывает. В Claude/Codex pre matcher для Grep отсутствует, поэтому дефект там относится к границе охвата хука, а не к тому же пути классификации. Ожидалось ограничение поиска в секретном файле под taint. **Влияние:** содержимое `.env` может быть прочитано и показано модели через поисковый инструмент. **Исправление:** классифицировать пути/маски файлового поиска, включая массивы путей и варианты host payload; подтвердить, какие поля реально передаются каждым адаптером. **Приёмка:** tainted Grep по `.env` блокируется там, где pre-hook существует, обычный поиск по коду проходит; тесты используют реальные схемы payload, когда они будут записаны.

### A-08 · P1 · Высокая · M — валидный JSON состояния может снять taint

**Условие и наблюдение.** [FileSessionStore.read](../../packages/core/src/taint/session-store.ts#L41) проверяет синтаксис JSON, но приводит объект к `SessionState` без проверки формы. Синтетический файл с `taint.level: 'BROKEN'` загрузился, и `curl` получил `allow`, поскольку [policy](../../packages/core/src/policy/evaluate.ts#L4) сравнивает значение строго с `suspect`. Ожидалась ошибка и блокировка high-impact действия при нечитаемом состоянии. **Влияние:** повреждённое или несовместимое состояние может выключить ограничения без явного сигнала. **Исправление:** валидировать схему на загрузке; неизвестные уровни считать повреждением и отвечать fail-closed. То же правило применить к полям provenance; для производного индекса секретов предусмотреть безопасную перестройку. **Приёмка:** некорректные, но parseable JSON-состояния не приводят к `allow` на сетевое действие. Старые совместимые форматы следует явно описать и проверить до миграции.

### A-09 · P2 · Высокая · M — устаревший lock может перекрыть активный

**Условие и наблюдение.** [withLock](../../packages/core/src/util/lock.ts#L19) удаляет каталог lock после `staleMs` (по умолчанию 10 с), не устанавливая владельца и не проверяя его при освобождении. В синтетическом тесте с сокращённым временем A держал lock, B удалил его и вошёл одновременно, а освобождение A позволило войти C, пока B ещё работал: `maxConcurrent=2`. Ожидалась взаимная исключительность. **Влияние:** при долгих файловых операциях возможны потеря обновления, дублирующиеся seq или разрыв audit hash chain. [AuditLog.append](../../packages/core/src/audit/audit-log.ts#L178) каждый раз перечитывает весь растущий лог, поэтому вероятность длинного владения увеличивается с размером файла. **Исправление:** lease с идентификатором владельца и проверкой перед удалением; не отбирать lock у живого владельца только по возрасту. **Приёмка:** несколько обработчиков с операцией дольше stale-порога сохраняют `maxConcurrent=1`; аудиторская цепочка и последовательность записей остаются целыми.

### A-10 · P2 · Высокая · S — trust и provenance дают противоречивые решения

**Условие и наблюдение.** Проверенный точным digest текст дал `post: suspect, trusted:true, taint:null`, но содержащаяся в нём команда затем получила `origin.suspect` и `deny-origin-suspect`: [engine.post](../../packages/core/src/engine.ts#L416) записывает provenance как подозрительный, игнорируя trust. Ожидалось понятное и согласованное действие waiver. **Влияние:** пользователь доверил файл для устранения ложного срабатывания, но всё ещё не может выполнить связанную с ним команду. **Исправление:** определить waiver как исключение и для taint, и для `origin.suspect`, сохранив факт срабатывания в аудите; либо явно ограничить смысл `trust` в CLI/документации и предложить отдельный путь разблокировки. Предпочтителен первый вариант. **Приёмка:** доверенный точный контент не даёт `origin.suspect`; изменённый байт возвращает исходную защиту. Это ослабляет блокировку только для явно доверенного содержимого.

### A-11 · P2 · Высокая · S/M — PowerShell путает последовательность с конвейером

**Условие и наблюдение.** [classify-powershell.ts](../../packages/core/src/actions/classify-powershell.ts#L168) даёт `shell.exec_encoded` и для `iwr URL | iex`, и для `iwr URL; iex`, хотя во втором случае вывод `iwr` не передаётся на выполнение. Ожидалось различать разделители. **Влияние:** лишняя безусловная блокировка обычной последовательности команд и неверное объяснение отказа. **Исправление:** сохранять тип разделителя в PowerShell-классификаторе и связывать fetch с исполнением только при фактической передаче данных/явном общем файле или переменной. **Приёмка:** pipe блокируется, независимая последовательность не получает `shell.exec_encoded`; тест покрывает обрамляющие кавычки и вложенный PowerShell.

### A-12 · P2 · Высокая · M — release staging не закреплён за проверенной версией

**Условие и наблюдение.** [release.yml](../../.github/workflows/release.yml#L3) реагирует на любой тег `v*`, но не сравнивает его с версией пакета перед `npm stage publish`; release job выполняет `pnpm test` и сборку, без остальных критичных CI-проверок. Ожидался отказ для несовпадающего тега и для commit с проваленными rules/coverage/typecheck/reports. **Влияние:** можно подготовить к 2FA-утверждению пакет из неверной версии или неполностью проверенного commit. **Исправление:** сравнивать `GITHUB_REF_NAME` с `v${package.version}`, ждать зелёный CI именно этого SHA или повторять критичные gates до staging. **Приёмка:** неверный тег и устаревший generated report не доходят до публикационного шага. Нынешнее ручное утверждение staged-пакета снижает риск распространения, но не исправляет gate.

### A-13 · P2 · Средняя · S — версия npm для staged publishing не фиксирована

**Условие и наблюдение.** [release.yml](../../.github/workflows/release.yml#L27) выбирает Node 24, затем выполняет `npm stage publish`. [Документация npm](https://docs.npmjs.com/staged-publishing/) требует npm 11.15.0 или новее; локальный Node 24.13.1 поставляется с npm 11.8.0, где `npm stage` отсутствует. Версия на текущем GitHub runner не проверялась. **Влияние:** staging может зависеть от того, какую minor-версию Node 24 выдаст runner. **Исправление:** закрепить совместимый npm и явно проверять его версию до публикационных шагов. **Приёмка:** workflow подтверждает `npm stage --help` на выбранном runner; отсутствие команды даёт понятный отказ до попытки публикации.

### A-14 · P2 · Высокая · S/M — документы и сайт описывают прежнее поведение

**Условие и наблюдение.** Производственный бюджет сканера — 4 000 мс в [scanner.ts](../../packages/core/src/scan/scanner.ts#L56), но README, шаблон генерируемого BENCH и сам BENCH говорят 500 мс. ## Документированные ограничения и непроверенные гипотезы

Это не новые подтверждённые обходы, но они определяют реальную границу продукта и следующий объём работы.

| Область | Состояние и влияние |
| --- | --- |
| Хуки как механизм | Их можно отключить или обойти настройками хоста; сбой запуска хука не всегда блокирует действие. Проверять фактическое состояние через `doctor`/`exposure`, после исправления A-06. |

| Секретный egress | Точное совпадение и URL-декодирование работают в проверенных случаях. Разделение значения по аргументам, позднее shell-расширение, некоторые формы URL и заголовки WebFetch остаются известными границами. |

| Audit hash chain | Проверяет изменение/удаление записей внутри журнала; удаление хвоста без внешнего якоря не обнаруживает. Это описанный предел, не новый дефект. |
| Regex и таймер | Бюджет проверяется между правилами/вариантами и не прерывает одно зависшее регулярное выражение; нужен worker isolation. |

### Дополнение: проход по этапу 3

- **Cursor.** По [актуальному контракту Cursor](https://prod.cursor.com/docs/hooks) добавлен `preToolUse` с точным matcher `Write|Delete` и `failClosed: true`. Все распознанные поля пути проверяются до действия, отсутствие читаемого пути и список более 64 путей дают явный deny. `ask` превращается в deny, поскольку Cursor принимает это значение в схеме, но не применяет его в `preToolUse`. `afterFileEdit` теперь записывает только post-наблюдение `cursor-edit-observed`. `doctor` требует этот gate и matcher. Синтетические регрессии подтверждают защиту `.cursor/hooks.json`, альтернативного поля пути и отказ для неизвестной формы. Живой Cursor и его Tab-правки **не проверены**; поддержка заявлена только для документированных Write/Delete событий.
- **MCP-имена.** Разбор `mcp__server__tool` теперь отделяет сервер по первому `__`, сохраняя `write__file` как имя инструмента. Регрессия показывает классы `config.self` и `mcp.side_effect` для такого имени. Составные имена серверов с `__` остаются неоднозначными без экранирования на wire; Cursor и прокси санитизируют сегменты, а реальный payload Claude Code не записан.
- **Длинный журнал.** Повторные append в одном процессе используют кэш последней записи, только если под lock совпали inode, размер, mtime и ctime; после append сверяется фактический хвост. Внешняя запись или правка сбрасывает кэш и возвращает полный разбор, включая отказ на повреждённой строке. На 1 600 синтетических append через разные экземпляры `AuditLog` в одном процессе: первые 100 p50 0,434 / p95 0,643 / max 4,528 мс, последние 800 p50 0,396 / p95 0,560 / max 1,311 мс; `verify` — 1 600 записей, `ok`. Это отдельный прогон без `tsx`-loader RSS-замера исходного аудита, поэтому показатели памяти напрямую не сравниваются. Каждый новый CLI-процесс по-прежнему разбирает существующий журнал целиком: межпроцессный checkpoint или ротация требуют отдельного проекта с сохранением семантики обнаружения повреждений.
- **Ложные срабатывания.** Три из четырёх совпадений — дословные примеры `curl … | sh` в README APISIX, Hugging Face Hub и Pulumi; тот же шаблон используется в инъекционных сценариях. Четвёртое — шаблонный `-----BEGIN PRIVATE KEY-----xxxx` в документации Prometheus, совпадающий с голым заголовком ATR-правила. Контекстный фильтр только для README уже терял две атаки при предыдущей проверке; снижение цифры 4/25 таким подавлением было бы ухудшением защиты. Для приёмки отдельной эвристики нужен независимый набор с размеченным намерением автора и сохранённые attack/fuzz gates. Текущие четыре остаются измеренной ценой высокочувствительных правил, не исправленным дефектом.
- **MCP Tasks и зависимости.** [Расширение Tasks](https://tasks.extensions.modelcontextprotocol.io/specification/draft/tasks) по состоянию на 23 сентября 2026 г. всё ещё помечено draft; завершённый `tasks/get` несёт вложенный `result`, а `notifications/tasks` может нести тот же результат без пары request/response. Для полного покрытия понадобятся также проверка исходящего `tasks/update` и cloak вложенного результата. Частичное добавление одного метода в список сканирования создало бы ложное обещание защиты, поэтому интеграция остаётся явно неподдерживаемой до полного протокольного набора и fixtures. Повторный `pnpm audit --prod --json` завершился `fetch failed`; advisories полного графа не проверены.

**Проверка после этого прохода:** coverage — 177 файлов, 2 773 теста, строки 96,41%, ветви 87,21%; typecheck, build, format-check, rules, ATLAS, benchmark-корпус и генерируемые отчёты прошли. Собранный CLI: attack 15 deny / 5 ask / 0 allow; fuzz 0 смысловых пропусков из 350; benign benchmark 4/25 ложных срабатываний, самый медленный файл 395 мс при лимите 4 000 мс. Новых реальных payload внешних агентов не получено.

На диске оставалось около 177 МиБ. Последняя небольшая правка, сделанная после зелёного прогона, была отменена. Состояние зависимостей и итог повторной проверки зафиксированы ниже.

**A-15 · Зависимости · P3 · высокая уверенность · S — низкоприоритетный advisory в dev-графе.** В [pnpm-lock.yaml](../../pnpm-lock.yaml#L769) закреплён `esbuild@0.27.7`, транзитивно через Vitest/Vite и tsup; `pnpm audit --json` нашёл один low-severity [GHSA-g7r4-m6w7-qqqr](https://github.com/advisories/GHSA-g7r4-m6w7-qqqr), тогда как `pnpm audit --prod --json` вернул 0 advisories для двух production-зависимостей. Условие эксплуатации согласно первичному advisory — запуск dev-сервера esbuild с `servedir` **на Windows**; запрос с backslash traversal может прочитать файл вне servedir. В исходниках/скриптах Stroq вызов `esbuild serve` не найден, и macOS-прогон не доказывает поведение Windows. Ожидалась версия вне уязвимого диапазона; фактически lockfile содержит 0.27.7. **Влияние:** риск для разработчика, запускающего такой dev-сервер на Windows, не подтверждённый дефект поставляемого CLI. **Исправление:** обновить совместимые dev-зависимости либо pin/override до `esbuild >=0.28.1` без нарушения их контрактов. **Приёмка:** полный `pnpm audit --json` без этого advisory, build/coverage проходят; Windows-сценарий при наличии dev-сервера проверен отдельно. Возможны несовместимость инструментов сборки и изменение lockfile; это не блокирует текущий production-аудит, но остаётся в backlog.
