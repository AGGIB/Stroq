# MCP stdio proxy — design spec (2026-09-07)

**Goal.** `stroq mcp -- <server command>` wraps any stdio MCP server so that every `tools/call` an MCP client makes goes through Stroq's policy before it reaches the server, and every result the server returns is scanned before it reaches the model — content scan + session taint, provenance, secret egress guard, ordered policy, hash-chained audit — for clients that have no hooks at all (Claude Desktop, and any `mcpServers`-style client) and as a second layer for the ones that do. `stroq init --agent mcp` rewrites a client's MCP config so its stdio servers start through the proxy.

**Sources (fetched 2026-09-07).** Official: `modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio` (framing), `…/basic/index` (JSON-RPC rules, ids, `_meta`, error codes), `…/server/tools` (`tools/list`, `tools/call`, result shapes, `isError`, error semantics), `…/basic/patterns/mrtr` (multi round-trip results), `…/changelog` (what 2026-07-28 changed: no `initialize`, `server/discover`, `resultType`, tasks moved to an extension, deprecated sampling/roots/logging), the 2025-06-18 `server/tools` page (the legacy shape), `modelcontextprotocol.io/quickstart/user` (Claude Desktop config path), `docs.windsurf.com` (Windsurf `mcp_config.json`, `serverUrl` for HTTP servers), the Inspector's "protocol eras" page (legacy vs modern negotiation on stdio). Cross-checked with `sheeki03/tirith` (a stdio gateway: batch arrays denied fail-closed, unmatched calls forwarded transparently), `technosiveuk-ui/SentinelMCP` and `eqtylab/mcp-guardian` (HTTP/stdio proxies that approve or deny individual tool calls).

## 1. What MCP gives us

| Item | Contract |
| --- | --- |
| stdio framing | The client launches the server as a subprocess. One JSON-RPC message per line on stdin/stdout, no embedded newlines; the server's stderr is free-form logging the client may forward or ignore. Nothing but MCP messages on the two streams. The same framing works over any byte stream. |
| Eras | **Legacy** (2024-11-05 … 2025-11-25): `initialize` / `notifications/initialized` handshake, server-initiated requests on stdout (`sampling/createMessage`, `elicitation/create`, `roots/list`) answered by client-written responses, `ping`, JSON-RPC batch arrays (2025-03-26 only). **Modern** (2026-07-28): stateless — no handshake; every request carries `_meta["io.modelcontextprotocol/protocolVersion"]` and client capabilities; `server/discover` (also used as a compatibility probe on stdio); every result carries `resultType: "complete" \| "input_required"`; server-to-client interactions ride in `InputRequiredResult` replies (MRTR), never as stdout requests; `subscriptions/listen` for list-changed notifications; tasks are an extension (`io.modelcontextprotocol/tasks`, results polled through `tasks/get`). Real servers are overwhelmingly legacy today; a client may probe `server/discover` first and fall back to `initialize`. |
| `tools/list` | Request `{ method: "tools/list", params?: { cursor } }`; result `{ tools: [{ name, title?, description?, inputSchema, outputSchema?, annotations?, icons? }], nextCursor?, (modern) resultType, ttlMs, cacheScope }`. Descriptions and annotations are **untrusted** content the model reads. |
| `tools/call` | Request `{ id, method: "tools/call", params: { name, arguments?: object, (modern retry) inputResponses?, requestState? } }`. Result `{ content: [{ type: "text", text } \| image \| audio \| resource_link \| resource], structuredContent?: any, isError?: boolean, (modern) resultType }`, or an MRTR `{ resultType: "input_required", inputRequests?, requestState? }` after which the client retries with a NEW id. A protocol error is a JSON-RPC `error` (`-32602` invalid params for an unknown tool); a tool execution error is a result with `isError: true`, which clients SHOULD show the model so it can self-correct. |
| ids | Never `null`; unique per sender. Client-request ids and server-request ids (legacy) are separate namespaces on the same pair of streams. `notifications/cancelled { requestId }` cancels an in-flight request. |
| Client configs (stdio entries) | Claude Desktop: `~/Library/Application Support/Claude/claude_desktop_config.json` (macOS), `%APPDATA%\Claude\claude_desktop_config.json` (Windows), `~/.config/Claude/claude_desktop_config.json` (Linux). Windsurf: `~/.codeium/windsurf/mcp_config.json` when it exists (current IDE builds write it there; two third-party installers target it), else `~/.codeium/mcp_config.json` (the path the docs name). Cursor: `.cursor/mcp.json` (project), `~/.cursor/mcp.json` (user). Claude Code: `.mcp.json` (project). All share the shape `{ "mcpServers": { "<name>": { "command", "args"?, "env"?, "cwd"? } } }`; HTTP servers use `url`/`serverUrl` (+ `headers`) instead and are out of scope. VS Code (`.vscode/mcp.json`, key `servers`) and Codex (`config.toml`, `[mcp_servers.<name>]`) use other shapes and are out of scope for v1. |

## 2. Adapter contract

Three parts: the long-running **proxy** (`stroq mcp`, `packages/cli/src/commands/mcp.ts` + `packages/cli/src/mcp/*.ts`), the **installer** (`stroq init --agent mcp`, `packages/cli/src/commands/mcp-config.ts`), and a `doctor` line. The engine, rules, policy, secret index and audit are the shared ones; the proxy is one more adapter in front of them.

### 2a. `stroq mcp` (the proxy)

- **Invocation** (what `init` writes): `"<node>" "<entry>" mcp --server <name> --client <client> --cwd <dir> -- <command> [args…]`. `--server` is the config key the entry had (the trusted server name — never read from the wire); `--client` names the client (`claude-desktop`, `windsurf`, `cursor`, `claude-code`, or the config file's basename for `--config`); `--cwd` is the project directory `init` ran in (Claude Desktop launches servers from `/`, so the project has to be recorded); `--session <id>` optional. Everything after `--` is the original command line, spawned verbatim with the proxy's own environment (the client already applied the entry's `env` to the proxy process, so the server inherits it unchanged) and with the working directory the client gave the proxy, not `--cwd`. Missing `--server` or missing `--` → exit 2 with a usage error on stderr before anything is spawned.
- **Session** = `--session`, else `mcp:<client>` — every proxy of one client shares one Stroq session, so a poisoned result from server A taints the calls that go to server B. **Policy cwd** = `--cwd`, else `process.cwd()`. Nothing on the wire can change either.
- **Engine**: created once per process (`createEngine()`); the secret index re-reads its sources on change as it already does. Messages are processed **strictly in arrival order per direction** (one queue per stream), so audit order matches wire order and the session lock never overlaps.
- **Client → server** (proxy stdin): each line is parsed as JSON. A `tools/call` request (`method === "tools/call"`, an `id`) → `engine.pre({ sessionId, toolName: mcpToolName(server, params.name), toolInput: params.arguments as a record (`toolInputRecord`: object, JSON string, bare value → `raw`), cwd })` — the record is the arguments as they are, never reduced, so the secret egress guard scans every field; `inputResponses`, when present, are appended to the record under `inputResponses` so a retry is judged on what it carries. **allow** → the ORIGINAL line is forwarded byte-for-byte and `id → { name }` is remembered as pending. **deny** → the line is NOT forwarded; the proxy writes to its stdout, with the same `id`, a tool result `{ jsonrpc, id, result: { content: [{ type: "text", text: "Stroq blocked this action (<rule>): <reason> Evidence: …" }], isError: true, resultType: "complete" (only when the request carried `_meta["io.modelcontextprotocol/protocolVersion"]`) } }` — a tool execution error, which the spec says clients SHOULD show the model, rather than a JSON-RPC protocol error, which they need not. **ask** → the same shape with the Codex wording: `Stroq would ask before this action (<rule>): <reason>. An MCP proxy cannot prompt, so it is denied; run it yourself or relax the rule in ~/.stroq/policy.yaml.` — lossy on the wire, never in the audit. An unreadable-but-non-empty `params.arguments` cannot happen for an MCP call (the record is whatever arrived); a `tools/call` without a string `params.name` is malformed and answered with `isError: true` `mcp-proxy-malformed-call` without forwarding. Every other client message — `initialize`, `server/discover`, `tools/list`, `resources/*`, `prompts/*`, `ping`, notifications, and client RESPONSES to legacy server-initiated requests — is forwarded unchanged; `tools/list`, `resources/read` and `prompts/get` requests are remembered as pending so their results can be scanned. A JSON-RPC **batch array** that contains any `tools/call` is answered fail-closed: one `isError` result per `tools/call` in it (`mcp-proxy-batch`) and a `-32600` error for the other requests, nothing forwarded; an array with no `tools/call` is forwarded unchanged. A line that is not JSON is forwarded unchanged (the client is trusted on framing; only the server is the adversary) and logged at debug.
- **Server → client** (server stdout): each line is parsed. A response whose `id` is pending: for `tools/call` → `engine.post({ sessionId, toolName: mcp__<server>__<tool>, toolInput: { method: <the pending request's method> } (no argument values, so the post audit summary stays readable without repeating secret-shaped data), toolResultText: mcpResultText(result), cwd })` where `mcpResultText` joins every `content[].text`, embedded `resource.text`, `resource_link` `name`/`uri`/`description`, `structuredContent` as JSON, and, for an `input_required` result, `JSON.stringify(inputRequests)`; `isError` results are scanned too (a poisoned error text is still content the model reads). For `tools/list` → `engine.post` with toolName `mcp__<server>__tools_list` and the text of every tool's `name`, `title`, `description`, `annotations` and `inputSchema` (as JSON text — a parameter's own `description` inside it is exactly as model-visible a rug-pull surface as the tool's own); for `resources/read` → `mcp__<server>__resources_read` with `contents[].text`; for `prompts/get` → `mcp__<server>__prompts_get` with every message's text. A `tools/call` result whose scan came back **suspect** is forwarded with one extra text block appended to `content`: `{ type: "text", text: "⚠ <warningFor(...)>" }` — the only channel that reaches the model in MCP; nothing else in the result is altered, `structuredContent` included. Suspect `tools/list`/`resources/read`/`prompts/get` results are forwarded unchanged (taint only). An `input_required` reply keeps the `id` pending for nothing: the retry arrives with a new id and is judged again. A pending entry is dropped on its response, on `notifications/cancelled` for its id, or when the table exceeds 4096 entries (oldest first). Everything else — server notifications, legacy server-initiated requests, responses to ids the proxy never saw, non-JSON lines — is forwarded unchanged; the server's stderr is piped to the proxy's stderr unchanged.
- **Fail-closed where it matters, transparent elsewhere**: an engine error (or a throw anywhere) while judging a `tools/call` request → the deny shape with `Stroq internal error (fail-closed): <message>` (never forwarded); an engine error while scanning a result → the result is forwarded unchanged and the error is logged (`logError`), the same observe-only trade-off the hook adapters make on `post`. The proxy never rewrites a forwarded line (byte-exact forwarding, including whitespace and key order) except for the appended warning block on a suspect `tools/call` result, which is re-serialised.
- **Lifecycle**: the server is spawned with `stdio: ['pipe', 'pipe', 'inherit']`; when the proxy's stdin ends the server's stdin is ended and the proxy waits up to 2 s before `SIGTERM`, then `SIGKILL` 2 s later; when the server exits the proxy flushes and exits with the server's code (or 1 on a signal); `SIGINT`/`SIGTERM` to the proxy are forwarded to the server. A server command that cannot be spawned → exit 1 with the error on stderr (the client reports a failed server; nothing is bypassed because nothing runs). Backpressure: writes honour `drain`; a single line above 8 MiB is forwarded without being parsed and logged (a `tools/call` request that large is still judged: the parse limit applies to server output only — client lines are always parsed).
- **Audit**: `engine.pre`/`engine.post` audit as for every adapter; the proxy's own denies (`mcp-proxy-malformed-call`, `mcp-proxy-batch`) are recorded through `denyDirectly`. The tool name in the audit is `mcp__<server>__<tool>`, so `stroq log`/`why` read the same as for MCP calls seen through hooks.

### 2b. `stroq init --agent mcp` (the installer, `commands/mcp-config.ts`)

- Targets one config file: `--client claude-desktop | windsurf | cursor | claude-code` (the paths in §1; `cursor` and `claude-code` are project files under the current directory, `--user` picks Cursor's `~/.cursor/mcp.json`) or `--config <path>` for any file with an `mcpServers` object. Exactly one of the two.
- For every `mcpServers` entry that has a `command` and is not already wrapped: rewrites it to `{ command: "<node>", args: ["<entry>", "mcp", "--server", "<name>", "--client", "<client>", "--cwd", "<cwd>", "--", "<original command>", ...originalArgs], env: <unchanged>, ...every other key unchanged }`. `<node>`/`<entry>` are the same `hookCommand` pieces the other installers use (argv form, like the OpenClaw plugin's `stroq.json`; `--import tsx` inserted in development exactly as `hookArgv` does). Entries with `url`/`serverUrl` (HTTP) are left untouched and listed in the output as skipped. An entry is **already wrapped** when its `args` contain `"mcp"` immediately after a Stroq entry path and `"--server"`; re-running replaces the wrapper (an upgrade updates the entry path) rather than wrapping twice — the original command is recovered from after `--`. `--dry-run` prints the rewritten file to stdout and writes nothing. Keys, order and unrelated entries are preserved; the file is written with `writeJsonObject`. A missing file is an error for `--client`/`--config` (there is nothing to wrap), not a create.
- Prints per entry `wrapped <name>` / `already wrapped <name>` / `skipped <name> (http)`, then the note: restart the client for the change to take effect; the proxy records this directory as the project for the secret index and path rules; an `ask` is rendered as a block naming the rule (an MCP proxy cannot prompt); HTTP servers are not covered.
- `stroq init --agent mcp --unwrap` restores every wrapped entry to its original command (needed to remove Stroq cleanly; the proxy binary path changes on upgrade otherwise). Same output lines with `unwrapped <name>`.

### 2c. `stroq doctor`

- An `mcp proxy` line per known client config that exists (Claude Desktop, Windsurf user file, Cursor project + user, Claude Code project): `wrapped N/M stdio servers` (HTTP entries not counted); `not installed` when no known config has a wrapped entry; a config that does not exist is silently skipped. `ok` when at least one agent or proxy is installed.

### 2d. Core change (the only one)

`SELF_CONFIG_FILE` gains `claude_desktop_config\.json` and `mcp_config\.json` (the two user-level client configs, where an agent has no business writing and where unwrapping the proxy switches Stroq off); `PROTECTED_DIRS` is unchanged. `.mcp.json` and `.cursor/mcp.json` are deliberately NOT protected: adding an MCP server to a project config is a routine agent task, and denying it would be the bare-`.claude` false positive again. That gap is stated in the README and SECURITY.md (follow-up: a content-aware check that protects only the wrapped entries).

### 2e. Docs, demo, CI

README: "Supported today: … Windsurf (native hooks) · OpenClaw (in-process plugin) · any MCP client (stdio proxy)"; Install `--agent mcp`; a `### MCP proxy` subsection (what is judged, what is scanned, the warning block, limits); `packages/cli/README.md` the same; SECURITY.md scope; CHANGELOG under Unreleased; demo `examples/demo/run-mcp-demo.sh` with a fake stdio server `examples/demo/mcp-fake-server.mjs` (a tiny newline-JSON-RPC server: `initialize`, `tools/list` with one poisoned description, `read_issue` returning a poisoned text, `send_message` echoing its arguments) replayed through the built CLI with a scripted client: `tools/list` → taint; `send_message` with a `.env` value → `isError` deny (`deny-secret-egress`), never forwarded; `read_issue` → result forwarded with the appended warning; `send_message` with the URL the poisoned result planted → blocked by provenance/taint; a plain `get_time` → forwarded unchanged byte-for-byte; the secret grep is clean over every stream and the audit; CI step after the Windsurf demo.

## 3. Limits to state in the README

- **No `ask`.** A policy `ask` is rendered as an `isError` tool result that names the rule; the audit keeps the real `ask`.
- **stdio servers only.** HTTP (`url`/`serverUrl`) entries are skipped by `init` and unprotected; VS Code and Codex config shapes are not rewritten in v1.
- **The warning block modifies the tool result** the model sees on a suspect scan (one appended text item); `structuredContent` is untouched. Clients that validate `content` strictly still accept an extra text item.
- **Results delivered outside the `tools/call` response are not scanned**: the tasks extension (`tasks/get`), resource subscriptions, sampling/elicitation payloads inside legacy server-initiated requests.
- **The project directory is the one `init` ran in** (`--cwd`); a user-level config wrapped from another directory indexes that directory's `.env`, plus the home credential files as always.
- **Batches containing a `tools/call` are refused** (fail-closed); batching was removed from the protocol in 2025-06-18.
- **Session taint is per client**, not per conversation: Claude Desktop has no conversation id on the wire, so taint from one chat persists into the next until the session expires.
- `.mcp.json`/`.cursor/mcp.json` are not self-tamper protected (see §2d).
- The wire handling is built from the specification and three proxies, not recorded from a client; the demo's fake server is hand-written. Windows: the rewritten `command` is Node's absolute path, which works on Windows, but nothing is tested there.

## 4. Out of scope (v1)

HTTP/Streamable-HTTP proxying, tool-description drift/lockfile ("rug pull" detection beyond scanning descriptions on every `tools/list`), argument rewriting/redaction, human-in-the-loop approval channels, the tasks extension, VS Code/Codex/OpenClaw config rewriting, MCP-shaped `stroq attack` scenarios.

## 5. Test strategy

Framing and dispatch unit tests with an injectable engine (`packages/cli/src/mcp/*`): line splitting across chunks, non-JSON pass-through, request/response/notification classification, pending-id table incl. cancel and overflow, batch refusal, byte-exact forwarding, deny/ask/malformed shapes with and without `_meta`, result-text extraction for every content type, warning block appended only on suspect. Real-engine tests (temp `STROQ_HOME`, `process.chdir` helper as in the Windsurf tests): secret egress through nested arguments, `tools/list` poison → taint → a later side-effect call asked/denied, provenance from a `read_issue` result into a later call's arguments, unknown tool name sanitised (`mcpToolName`), engine error on pre → fail-closed deny, on post → forwarded. Process e2e: spawn `stroq mcp -- node <fake server>` from a temp project with `TSX_TSCONFIG_PATH` (as the Windsurf e2e does), drive it with a scripted client over stdin/stdout, assert the exact lines, exit codes and stderr pass-through, and that killing the client stdin terminates the server. Installer tests on temp copies of each client config shape (wrap, idempotent re-wrap, dry-run, unwrap, HTTP skipped, foreign keys preserved); doctor; demo in CI.
