# MCP tool-contract approval

This is an explicit strict-proxy mode. It has not been checked with a real MCP client or in a browser walkthrough.

This mode covers a stable MCP registration whose server changes an advertised tool name, description, input/output schema or behavior hints. Static inventory and pinned local code do not establish an approved advertised contract. An ordinary strict proxy scans messages; the opt-in mode adds exact-version approval before forwarding calls.

The workflow is: select an eligible installed stdio registration → **Protect & review tools** → inspect the configuration preview and consent to interruption/private metadata retention → reconnect its client → inspect **MCP tool review** → explicitly approve each exact advertised version → explicitly retry discovery or a call. Opening the console or reading records never launches the server. No first baseline is silently approved, and approval never repeats a call.

## Runtime behavior

- `stroq mcp --strict --tool-approval --pass-env <names> ...` opts in. Environment filtering must be explicit; `--cloak` is incompatible. Existing ordinary wrappers stay unchanged. In the console, an existing wrapper needs explicit recovery and a fresh Protect preview to change modes.
- Each connection requires a fresh root `tools/list`, full strict reading/scanning and a complete capture before any call can pass. Saved complete captures are historical observations, not a current-client health signal. Connection-local authority ends synchronously only when the contract may have changed or the proxy can no longer follow the server: a client `tools/list`, `list_changed`, a server line it cannot read (too long, not JSON, not one object, a repeated key), a reply to no open request or a second reply, a reply envelope JSON-RPC does not define, a listing that cannot be captured, and either side using the proxy's private request IDs. Ordinary events are handled for their one message and leave every approval as it was: a cancelled call (its late reply is dropped), a client message Stroq cannot read exactly (refused with the reason, for example a repeated key or a number that cannot be represented exactly such as an integer beyond 2^53), a request that reuses an open or cancelled ID, a server log line or sampling request, and a call result that strict mode withholds (including one carrying such a number, which is never delivered rounded). Keys such as `constructor` or `__proto__` in a call or a result are data. Approval is never restored as connection freshness after restart.
- A root `tools/list` from the client starts one bounded capture through its **already running** server. The proxy follows opaque `nextCursor` values internally, scans each complete page, then scans the combined listing. It returns one complete result under the original client request ID, with no internal cursors or request IDs exposed. Client-selected continuation cursors are refused; clients receive the complete aggregate instead.
- Missing `nextCursor` ends a listing; null/empty/invalid cursors, cursor cycles, duplicate raw names across pages, unsupported list-level metadata or tool fields, lossy numbers, unsupported integer-key ordering, invalid Unicode and excessive nesting/size are refused. A timeout, cancellation or `list_changed` invalidates the unfinished walk. Such input cannot establish an approved empty list. The entire discovery response is withheld while any advertised version is pending or revoked. Individually approved calls still require the connection's complete fresh capture.
- Versioned hashes bind exact raw server/tool tuples, the full supported tool object, canonical workspace plus directory identity, declared environment digest, original invocation and the current adjacent CLI bundle bytes. Names containing colons cannot alias normalized audit labels. Supported tool fields include name, title, description, input/output schema, annotations, icons, execution and `_meta`; unknown fields are refused rather than omitted from authority. This does not validate the semantic truth of JSON Schema or annotations.
- The ordinary policy judgement and strict message scan remain independent. Immediately before the actual synchronous upstream write, a shared private-store lock checks the exact current capture/version decision again. Revocation applies to future physical dispatch; it does not undo queued, in-flight or completed server work. It is not process termination.

## Review and retention

`/skills/mcp/contracts/` reads only current, exactly matched opted-in registrations. A changed runtime, declared environment, launch or registration cannot silently select another historical binding. A complete empty capture differs from no capture, invalidated capture and unavailable storage. The public projection has a 512 KiB bound; exceeding it reports unavailable rather than truncating a review.

Identical launches with the same client/name/context in multiple configuration scopes are ambiguous in this version. Review reports a context gap and refuses decisions; recover one registration explicitly or use distinguishable launches before reviewing. It never silently chooses a scope.

Full advertised descriptions and schemas are retained **unencrypted** under the private `<Stroq home>/store/mcp-contracts` directory, with 0700 directories and 0600 records. Metadata can itself contain secrets or hostile instructions. The UI displays complete retained contracts as inert text; it does not render Markdown, fetch icons/URLs or turn metadata into action arguments. Current capture bodies and the last explicitly approved full body per exact tool identity are retained with bounded decision history. This is not a complete archive of every observed or approved version. There is no automatic expiry/deletion. Same-OS-user edits remain outside this filesystem privacy boundary; the existing Stroq sandbox protects the store when that sandbox is actually in use.

Each record carries a `mac`: an HMAC-SHA256 under the home's state key, `<Stroq home>/keys/state-mac.key` (32 random bytes, mode 0600 in a 0700 folder, made by the first writer; the same key signs the [call-control history](mcp-call-control.md), each file under its own label). A record rewritten by anything that does not hold the key, with a plain digest in that field or a tag from another key, is refused as unverified (`tool-contract-invalid`): no call or listing passes, the review reports the record as one that could not be verified, and the file is kept as it is rather than replaced. A signed record found when the key is missing is refused the same way, and no writer makes a new key while such records exist; a key that is a link or readable by others makes the store unavailable. To recover, put the key back, or remove that binding's `store/mcp-contracts/binding-*.json` and approve its tools again. This is tamper-evident, not a boundary: a process running as the same user that can read the key, or write a key of its own into `keys/` (it does not need to read anything) and sign again, gets through. Stroq's hooks deny an agent's writes under `~/.stroq`; `stroq run --sandbox` write-protects `keys/` and `store/`.

The signature does not stop a rollback. A writer that kept an older record this home signed (from before a revocation, say) can put it back before a proxy starts, and it verifies: that proxy honours the old approval. Nothing a process of the same user cannot write records which record is the newest. What holds is narrower: every write raises a `sequence` inside the signed body, and a running proxy remembers the highest it has accepted per binding and refuses a lower one as unverified (`tool-contract-invalid`), so a record put back while it runs withholds calls instead of approving them. A record removed while it runs counts as absent, and the proxy's next write goes above what it has seen.

Comparison always uses the last explicit approval: approved A → pending B → pending C still compares C with A. Observation, invalidation, tool removal and revocation preserve that evidence; they never accept a new baseline. An exact approval atomically records the new body, hash, identity and approval time under the existing decision lock. Revoked authority can therefore coexist with an unchanged comparison; matching an old body does not itself grant permission.

The review shows added, changed and removed JSON fields before the complete bodies. Object keys are compared deterministically; arrays are compared as ordered whole values, and missing differs from JSON null. All supported hash-covered fields participate. The summary describes changes, not safety or schema compatibility. Comparison is bounded to 256 change paths and 64 KiB of UTF-8 pointer paths, with depth/node limits. Exceeding a bound hides partial counts and reports an incomplete comparison; full captured bodies remain available for exact manual review. Preparing a decision displays that preview's own bodies and comparison.

New private records use version 3, the first signed one. Records written before signing (versions 1 and 2) are not read as authority: they count as absent, so none of their approvals, history or retained bodies is used. Opening the review shows such a registration with no capture and changes nothing; the next listing through the proxy replaces the record with a signed one that has no approvals, the proxy withholds the tools as not approved, and each tool is approved again in **MCP tool review**. No observation or repeated no-op decision fabricates a historical body. Retained bodies are re-canonicalized and checked against their binding-derived identity, hash and latest approval event before use or publication.

Listing walks allow at most 16 pages in 30 seconds, 256 tools, 200,000 serialized JSON characters and 1 MiB of aggregate JSON bytes; strict scanning can refuse a smaller capture. Opaque cursors are bounded to 4,096 UTF-8 bytes and are never parsed, fetched or retained across walks. The proxy reserves the `stroq-tools:` JSON-RPC ID prefix for its internal requests. Explicit cancellation of a held walk is handled at ingress and produces no late client reply; it cannot recall bytes already written. A failed first capture is retained as incomplete with no complete capture SHA; a genuine complete empty listing remains distinct.

Storage limits are 64 bindings, 64 KiB per tool, up to 256 approved baselines with 1 MiB of aggregate retained body bytes, 2 MiB per record, 32 MiB aggregate and 1024 decision events per binding. Capture depth/node bounds are conservative. Malformed, unverified or over-limit authority is never silently reset, pruned or overwritten; only an unsigned record from before version 3 is replaced, by the next listing, as described above. Complete serialized records are validated before atomic publication. Runtime graph revalidation has an I/O cost on gated operations.

Approve/revoke uses a short-lived preview tied to the exact current registration, binding, capture SHA, raw tool-derived ID, contract SHA and private record revision. Separate acknowledgements precede apply. Compare-and-swap rejects stale choices and replayed previews. Opening, refreshing or preparing a preview makes no decision. A lost acknowledgement remains unconfirmed; a new action requires an explicit exact recheck. When its binding/version has disappeared, a full page reload still begins with fresh source reads and a new explicit review, never an automatic retry.

Authenticated same-origin endpoints are `GET /api/mcp-tool-contracts` and `POST .../preview`, `POST .../apply`. Selectors are opaque IDs/hashes; paths, arbitrary commands, duplicate keys and query selectors are refused. Overlapping identical reads share only their in-flight source read; completed snapshots are never cached as current. Decisions keep their separate exclusivity and final source/CAS checks. The console exposes no generic server runner.

This control binds an advertised interface. It cannot prove the server implements that interface honestly or detect an undeclared change of behavior. Native-client adoption, sandboxing, code-tree pins and runtime policy decisions remain separate evidence.
