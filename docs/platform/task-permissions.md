# Task permissions

**Agents & coverage → Task permissions** inspects existing Stroq Task Lock permits for the selected canonical workspace. It shows signed tool, file, network and MCP grants, the validity window, recorded mode, terminal markers and captured task evidence. The current launcher supports Claude Code. Inspection does not start an agent or read a private signing key. Fresh signed refusals have a separate explicit [one-use access workflow](task-access.md), with complete redacted review and signing consent.

The useful action is **Revoke**: review the exact permit, acknowledge that further task tool access will be interrupted, then create its native `revoked` marker. State and preview are read-only. Apply binds the permit bytes and file identity, public key, task and root directories, both terminal markers and the verified runtime. Invalid inputs or missing acknowledgement do not consume an otherwise current preview. Accepted previews are single-use, expire after two minutes and share an eight-plan / 8 MiB memory cap.

The writer holds the existing harden lock through worker termination and readback. It creates an empty private marker exclusively under captured existing parents. It does not replace a permit, signing key, policy or earlier marker. Core `FilePermitStore` must then report revoked, and an isolated evaluation of the real core task gate must return `task-void:revoked` / deny. A receipt records that evidence separately from host termination. A newly created safe `ended` marker after commit may be the launcher's normal cleanup and does not invalidate a confirmed revocation; an `ended` marker appearing before commit still refuses the stale preview. Unknown post-write completion requires a fresh GET before another action. There is no automatic apply retry or undo of this permit's revocation; a new task needs a new permit.

Revocation denies the next gated tool calls. The launcher stops the agent when it observes invalidity at a later gate evaluation. A marker or isolated gate result does not establish that an idle process has already stopped, cancel an action that already ran, or prove that a client is currently adopting the gate.

Existing tasks retain their launch-time policy object. Comparing a signed permit's policy digest with today's file detects a difference; it does not reload a running task or show that it adopted new rules. Protection groups such policy-review gaps and links to the ledger. The policy-apply receipt also points to task review. Unknown current policy, partial storage and unverifiable permits remain explicit.

## From a finding to its current permission

An explicit **Find task permission** action in a finding looks up the recorded task ID against the current signed permits for the selected workspace. Opening a finding does not start this lookup. The server first reselects the exact visible record, verifies the full bounded journal and matches the original raw-line fingerprint, sequence and timestamp. It refuses the core's invalid-ID sentinel, contradictory signed session bindings and events outside the current permit's validity window. Missing or invalid evidence stays unavailable rather than becoming “no task.” A valid append may be accepted only while the file identity and entire earlier byte prefix remain unchanged; replacement, rewrite and truncation are refused.

The ID lookup does not establish a historical permit revision. A match therefore means **the same recorded task ID has these current permissions**, not that this permit revision authorized the original event. Its report keeps `historicalPermitRelation: not-recorded`, including for newer records; only the separate signed access-request verifier can authorize one-use issuance. A handoff carries workspace, opaque task ID, expected current permit SHA and source finding ID. The permission page rereads the current ledger and blocks review of a substituted permit; opening current permissions requires an explicit new selection. The source ID is navigation metadata, not mutation authorization. Revocation still uses its independent exact-permit preview and acknowledgement; its receipt does not claim that the finding was resolved or that a process terminated. A return link opens the exact finding with all review statuses visible.

The derived lookup report can be exported with its finding. It includes the source and current journal fingerprints, capture time, current policy digest and explicit historical-revision limitation. It retains no raw task/session ID, journal text, command or signing data, writes no history, and never changes the finding's review state.

The reader authenticates the archived signature using the public key, then checks eligibility at the actual capture time with core expiry and clock-skew semantics. It does not reuse the CLI's archival `active` label. Revoked, ended, expired and not-yet-valid records remain distinct. A valid permit is recorded authority, not process liveness; `srt` and `hook-only` are signed declarations, not a new OS enforcement measurement.

Inspection pages contain at most 64 task candidates and read at most 64 KiB per permit (4 MiB per page), 4 KiB for the public key, a 16 MiB full journal and a 480 KiB public-row budget. The fixed native task directory is catalogued by names only, within 8192 directory entries, 1 MiB of name bytes and the worker deadline. Exact opaque-ID lookup hashes those bounded names and authenticates only the selected permit; it no longer depends on a permit appearing among the first 64 candidates. Known task IDs from a fully verified finding can be inspected directly without making unrelated archives an authority gate. Browser input never supplies a native ID or path.

The permission page has **First page**, **Back** and **Next page** controls. Continuations are opaque, server-held and expire after five minutes; at most 256 continuations / 1 MiB are retained in memory, and server restart discards them. Catalog/root/key/runtime drift refuses an old continuation instead of replacing it with the first page. Each page is its own current observation with a capture time; the UI does not merge pages into an atomic or complete report. A hard catalog limit remains explicit and cannot establish a requested task's absence. Existing `GET /api/task-locks` remains a first-page projection with incomplete coverage when more candidates exist.

Exact permission links read the selected task's containing page. New links carry its permit SHA; a different revision is a conflict, never a substitute. Legacy links without a permit SHA read the current authenticated version of that same exact task ID and make no historical-version claim. Revoke still prepares its own fresh exact-permit plan. Paging neither prepares a revoke preview nor acknowledges interruption, resolves an uncertain write, archives nor deletes any task.

If complete rows do not fit, they are omitted with incomplete coverage; an exact selected row is retained first within the existing output budget, and grant lists are never silently truncated. Foreign verified workspaces are filtered without resolving their signed paths. Corrupt, unsafe, missing-key or unreadable candidates cannot become an empty healthy state.

Full captured-journal consistency uses core chain hashing, with parity tests against `AuditLog.verify`. Task receipt pairing preserves host-reported, failed and unconfirmed outcomes. No raw journal is copied to scratch. Captured journal consistency does not establish independent authenticity or detect tail truncation; recorded task IDs and timestamps alone do not prove process liveness or attribution to a current permit revision. New signed refusal attestations bind only their specific review and launch context, as described in [one-use access](task-access.md).

The compact permission metadata uses opaque workspace-bound task IDs and permit fingerprints. Nonces, signatures, raw task IDs, commands, prompts, credential values, keys and absolute paths are excluded from that projection. Workspace/user-home patterns are relative; external or unsafe display patterns are withheld. Signed host patterns and MCP/tool grant names are permission metadata, rendered as text. The separate explicit one-use access review intentionally displays complete available redacted operation context to the authenticated local operator; it follows the distinct retention and redaction limits in [one-use access](task-access.md). No new console report history is persisted: native task permits, extensions and markers remain in the existing Task Lock store until separately removed. Read refresh never changes that store. Exports contain only their selected public projection and captured receipts.

The public API has fixed authenticated endpoints: `GET /api/task-locks`, `GET /api/task-locks/page`, read-only `POST /api/task-locks/page` with either an opaque cursor or an exact task ID and expected permit SHA (explicit null for a legacy current-version read), read-only `POST /api/incidents/task` with finding ID and expected evidence SHA, `POST /api/task-locks/preview` with an opaque ID and expected permit SHA, and `POST /api/task-locks/apply` with preview ID and interruption acknowledgement. Page requests reject query selectors, duplicate decoded keys, extra fields and arbitrary offsets. No endpoint accepts a path, command, environment map, signing material or permission grant. Worker work has time/memory/message bounds; the parent releases the shared mutation lock only after termination. The current console operation is supported on POSIX; Windows remains explicitly unsupported.
