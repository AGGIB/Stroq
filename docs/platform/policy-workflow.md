# Policy settings workflow

The Policies view edits the policy this local server resolves. It can deny selected action categories in every session context, require approval or deny for unmatched actions, lower the content detection threshold, and promote selected Ask rules to Deny. A preview validates the candidate and compares it with the exact current policy before the owner applies it.

The rule reference remains a separate documentation view. It is not the installed configuration. A saved policy is configuration evidence; a successful scenario replay is simulation evidence. Neither establishes that a running host blocks an action.

## Interface and state transitions

The settings sit beside a persistent preview. On small screens, the settings come first.

1. **Read current policy.** Show source, effective rule count, validation status and editable settings. First run with no data directory still shows the bundled default. Reading creates nothing.
2. **Edit a draft.** Changing any field invalidates the previous preview. Rule selection uses stable zero-based positions from the frozen policy because custom rule IDs are neither unique nor constrained to safe display text. Show known action classes and context; do not return arbitrary reasons, commands or YAML.
3. **Preview & test changes.** The server applies only the selected strengthening changes to a YAML document, validates the parsed result, then replays both current and candidate policies. Category controls explicitly replace superseded class predicates; unrelated rules, predicates and their comments remain in order. Show the exact field/effect changes, replacement counts and scenario counts.
4. **Review the result.** Block apply for validation errors or warnings, allowed attacks, unmet expectations, unjudged scenarios or a saved check whose expected decisions do not match the candidate. Info-only findings remain informational. New ordinary-work interruptions require explicit acknowledgement of the preview being applied. A stricter policy can disrupt legitimate work; passing attack scenarios alone is insufficient.
5. **Apply policy.** Submit the server's preview ID, expected raw-byte revision, candidate semantic fingerprint and any interruption acknowledgement. No general YAML, file path or shell command enters the write API.
6. **Confirm and refresh.** Show the saved fingerprint and backup receipt. New hook invocations load the policy. Running MCP proxies must restart to load it. Proxies started with the current [launch-policy continuity control](mcp-policy-continuity.md) withhold new `tools/call` dispatch when the parsed policy changes or becomes unavailable; refusal stays latched until restart, even if the file is restored. Older running proxies are not upgraded automatically. Display the restart requirement beside the receipt.

The form is strengthening-only: `allow → ask/deny`, `ask → deny`, a lower threshold, promotion of existing rules, and unconditional denial of selected categories. It does not expose arbitrary rule deletion/reordering, YAML editing, exceptions or relaxation. Category controls deliberately remove the selected classes from old predicates and replace them with a first-priority Deny rule; unrelated rule data is preserved. Existing custom policy warnings remain visible and can block apply even after an otherwise valid edit.

## Recorded event to action control

From an incident's current-policy comparison, **Draft action controls** opens a workspace-bound Policies URL containing only the incident fingerprint. Opening the URL only reads policy. **Load recorded actions** explicitly reselects that exact journal evidence through the comparison service and verifies that its current-policy hashes match the policy being edited. Invalid, duplicate, incomplete and foreign links cannot silently select another event. No category is inferred from the incident's broad display labels.

The owner can review or change the fixed category selection, then preview/test it. If both recorded-class scenarios already return Deny, loading the event selects no new mutation. This only describes the recorded class combination; the manual controls can impose a broader restriction. After a verified apply and readback, **Recompare event** returns to the same immutable finding. It does not mark the finding resolved, replay its original command or assert a native-client block.

These are category controls, not exact command/tool/domain rules. They affect all agents using this Stroq data directory, in clean and suspect contexts, and require a separate shared-scope acknowledgement even when no bundled ordinary-work scenario changes. Existing running MCP proxies must restart to load the policy; saving does not hot-reload an engine or retry a refused operation.

The core evaluator uses the first rule matching any of an action's classes. Appending a Deny could therefore be ineffective. The transform inserts a collision-safe Deny first, removes selected classes from older predicates, removes emptied rules and preserves the order/data of the remaining rules. The preview discloses removed/narrowed rule counts. Every class combination containing a newly controlled class returns Deny; combinations without those classes retain their prior decisions. Pairwise tests with every known companion class cover both taint states, and full lint/corpus replay still blocks independently unsafe or shadowed custom policies. An already universal denial is omitted; cleanup alone is not reported as a new protection.

## Saved policy checks

After a current-policy comparison, **Save regression check** captures the complete nonempty combination of recorded action classes and the exact current decisions for `none` and `suspect` session taint. The dialog displays both expectations before confirmation. The server reselects the exact incident/evidence fingerprint and rechecks the current semantic and raw policy revisions; the browser never supplies classes, expected effects, commands or content. These are current-policy expectations. The original taint state and policy version were not recorded.

Checks belong to the selected **Stroq home**, alongside its policy, and apply to every future policy candidate using that home across workspaces. Saving requires a separate shared-scope acknowledgement. The recorded source workspace is the console context used when saving; it does not establish which workspace or agent produced the journal event. Identical classes and expectations reuse the existing check and preserve its first source. Different expectations for the same class combination are a conflict; replacing them requires explicit removal first.

**Saved checks** at `/policies/checks/` reads the private store and evaluates its expectations against the current policy. Refresh performs local class-only evaluation; it never launches an agent, executes the original action or spends provider requests. Each check has two session contexts, and both must match exactly: a Deny differs from an expected Ask or Allow. Results remain separate from the bundled attack/ordinary-work scenarios. A missing store is an empty set; an unreadable, malformed or changed store is unavailable, never a passing empty result.

Every policy preview includes the captured check-store revision and the candidate's results. A mismatch blocks apply even when the bundled corpus passes. Apply holds the same snapshot lock used by save/remove through the policy write, so a changed check set requires a new preview. The Protection queue links current mismatches or unavailable evidence to Saved checks; matching checks, including a successfully read empty store, remain quiet.

The fixed file `<STROQ_HOME>/console/policy-cases.json` retains action classes, expected effects, creation time and source fingerprints locally until explicit removal. It survives restart, has no automatic expiry or eviction and accepts at most 64 checks. A full store refuses a new check. Removal requires the current store revision plus separate acknowledgements that it weakens the regression gate and applies across workspaces. It does not edit the active policy. Saving, matching or removing a check does not establish host adoption, live blocking, credential rotation or remediation.

## Local API contract

The authenticated same-origin server exposes `GET /api/policy`, `POST /api/policy/preview`, and `POST /api/policy/apply`. [policy-service.mjs](../../console/scripts/policy-service.mjs) returns `{status, body}` for these routes. The route layer enforces local authentication, origin/CSRF checks and bounded JSON.

- Inspection returns source, `expectedRawSha`, `policyFingerprint`, default effect, threshold, indexed rules, validation counts and `editable`.
- Preview accepts `{expectedRawSha, changes}`. Allowed changes are `defaultEffect`, `threshold`, `promoteRuleIndexes` and `denyActionClasses` (one to twenty distinct core action classes). Its response includes `previewId`, `expiresAt`, both semantic fingerprints, the raw revision, a sanitized effect diff, validation/simulation counts, blockers and acknowledgement requirements. `actionControl` is either null or the canonical class selection, removed/narrowed rule counts and fixed `any`/`stroq-home`/`hostEnforcement:false` scope facts.
- Every preview also returns `regressions`: the captured check-store `revision`, check counts and exact expected/actual decisions for both taint contexts. These results are distinct from `simulation.replayed.cases`; saved checks are not reconstructed command scenarios.
- Apply accepts `{previewId, expectedRawSha, candidateFingerprint, acknowledgeInterruptions?, acknowledgeActionScope?}`. A category-control preview requires `acknowledgeActionScope:true` independently of interruption consent. Its receipt includes time, current semantic and raw hashes, receipt ID and backup ID (or null for a newly created policy).
- Preview YAML and frozen baseline bytes stay in server memory; they are not returned to the browser or logged. At most eight previews are kept, each for ten minutes. Restart invalidates previews.

[policy-cases.mjs](../../console/scripts/policy-cases.mjs) supplies the authenticated saved-check routes:

- `GET /api/policy/cases` reads and evaluates existing checks without writing them. Its response identifies the selected workspace context, current policy hashes, store revision, records and class-only results with `hostEnforcement:false`.
- `POST /api/policy/cases/save` accepts `{incidentId, expectedEvidenceSha, expectedPolicyFingerprint, expectedPolicyRawSha, expectedStoreRevision, acknowledgeSharedScope:true}`. The service derives the classes and both expectations from fresh exact evidence; save can return `saved` or `unchanged` while preserving the first source.
- `POST /api/policy/cases/remove` accepts `{caseId, expectedStoreRevision, acknowledgeWeakenChecks:true, acknowledgeSharedScope:true}`. Save/remove receipts bind the case, resulting store revision and selected workspace context. If a submitted request receives no verifiable receipt, completion remains unknown until a successful explicit recheck; it is not permission to retry blindly.

[policy-engine-entry.ts](../../console/scripts/policy-engine-entry.ts) adapts the real engine. [policy-worker.mjs](../../console/scripts/policy-worker.mjs) runs it with a 256 MiB worker heap and a 75-second preview deadline. Inspection is serialized with other policy operations, preventing repeated GET requests from launching unbounded workers. Shutdown aborts the active worker.

## Concurrency and recovery

Semantic hashes alone cannot protect a comment-only owner edit. [policy-files.mjs](../../console/scripts/policy-files.mjs) also hashes exact bytes and represents absence with a null revision. Apply re-inspects the effective semantic fingerprint, including the bundled default when no override exists, and rechecks exact bytes immediately before replacement.

Reads/writes are limited to the server-selected home and fixed policy path. Reject symlinks, hard-linked files, wrong ownership, non-regular files, writable-by-other-users paths and policy files over 256 KiB. The form handles at most 512 rules. YAML aliases are read-only because editing one scalar could affect another alias reference. YAML serialization may normalize layout; comments and semantic rule data are retained, and the raw pre-image is backed up.

An absent home is frozen against its nearest safe existing parent. Inspection and preview leave it absent. Apply creates private directories only if the observed absence and parent identity remain unchanged; an interposed directory or link invalidates the preview.

The client binds previews to the exact loaded source and selected draft, and receipts to the acknowledged candidate/backup relation. A workspace or event URL change aborts outstanding requests and invalidates consent. Timeouts, late replies and mismatched receipts never become a successful apply; an uncertain operation requires a current-policy read before another change. A failed read removes the prior current-policy claim.

A same-directory temporary file is flushed and atomically renamed. Owner-controlled policy bytes are backed up at mode 0600 before replacement; directories created by this workflow use 0700. A private receipt records the intended before/after hashes before replacement so an interrupted operation can be inspected. A failed write never claims success. As with the existing harden writer, portable Node filesystem APIs leave a narrow check-to-rename race; the implementation does not claim OS-level compare-and-swap against uncooperative external writers.

The settings form remains strengthening-only. The separate **Change history** workflow selects a server-retained intent and backup, tests prior bytes against the exact current source and saved checks, and requires explicit reduced-protection, shared-scope and private-copy acknowledgements. A prior absent file offers the current bundled default explicitly. Restoration retains another recovery copy and verifies raw and semantic readback; stale sources are refused and uncertain writes require recheck. Legacy intent records do not establish completed application. See [tested policy recovery](policy-recovery.md) for the fixed API, limits and evidence boundaries. Backups are recovery evidence, not proof that every running process adopted a policy.

## Acceptance checks

- Inspecting the bundled default policy succeeds, with an info-only note about unmatched actions.
- Comparisons replay the bundled attack and ordinary-work scenarios; the current semantic fingerprint is that of the inspected custom policy, not the bundled default.
- Comments, custom rules, order and predicates survive allowed edits. Unknown inputs, weakening, invalid indexes and alias edits are refused.
- Reading/previewing an absent home creates no files. Apply creates private directories and the exact previewed policy.
- Comment-only changes, a newly appearing file/home, changed bundled defaults, an expired preview and a mismatched candidate fingerprint prevent apply.
- Invalid or incomplete tests prevent apply. New ordinary-work interruptions require acknowledgement.
- Saved expectations remain effective after restart and workspace changes. Candidate mismatches block apply; changing the check set after preview invalidates it. Corrupt or unsafe storage cannot be silently replaced with an empty set.
- Saving reselects exact visible journal evidence and freezes both policy revisions. Duplicate expectations preserve their first source, conflicting expectations require explicit removal, and unknown completion cannot become a successful save/remove.
- Private byte backups match the pre-image. Symlinks, hard links, oversized files, unwritable targets and unsafe backup directories never redirect a write.
- Two tabs cannot bypass serialization; closing the service cancels active workers. No raw source or arbitrary error text reaches an HTTP response.

These cases are exercised in [policy.test.mjs](../../console/scripts/policy.test.mjs), [policy-engine.test.mjs](../../console/scripts/policy-engine.test.mjs), [saved-check service tests](../../console/scripts/policy-cases.test.mjs), [store tests](../../console/scripts/policy-cases-store.test.mjs) and [policy/check-store locking tests](../../console/scripts/policy-cases-policy-lock.test.mjs). Build the local engine adapters before tests that use them.
